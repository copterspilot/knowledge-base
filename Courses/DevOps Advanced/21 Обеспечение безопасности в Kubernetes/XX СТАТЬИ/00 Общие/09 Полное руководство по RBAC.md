### **Статья: Полное руководство по RBAC: На практике**

#### **Введение**

Представьте, что вы управляете крупной компанией. У вас есть бухгалтер, который должен видеть финансовые отчеты, и менеджер по продажам, который должен работать с клиентской базой. Но вы не дадите бухгалтеру доступ к базе клиентов, а менеджеру — к бухгалтерским книгам. **Role-Based Access Control (RBAC)** в Kubernetes работает по тому же принципу. Это механизм, который позволяет точно определить, кто (пользователь или сервис) может что делать (глагол: get, list, create) с какими ресурсами (pods, services) в каком namespace. Как указано в `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices`, понимание RBAC критически важно для создания безопасной и стабильной среды. Эта статья проведет вас от теории к практическим шагам по настройке RBAC.

#### **Часть 1: Основы RBAC**

RBAC — это не просто настройка, это фундамент безопасности вашего кластера.

*   **Проблема:** Без RBAC любой пользователь с доступом к API-серверу может управлять всем кластером. Как указано в `Kubernetes Изнутри`, "администраторы в Kubernetes – это пользователи root в контексте кластера".
*   **Решение:** RBAC позволяет ограничить доступ до минимально необходимого.
*   **Как включить:** RBAC включается на сервере API с помощью флага `--authorization-mode=Node,RBAC`. В большинстве дистрибутивов (GKE, EKS, AKS) он включен по умолчанию.
*   **Ключевой принцип: Принцип минимальных привилегий.** Предоставляйте субъекту только те права, которые ему абсолютно необходимы для выполнения задачи.

#### **Часть 2: Ключевые компоненты RBAC**

RBAC строится на четырех основных компонентах.

1.  **Субъекты (Subjects):** Кто запрашивает доступ.
    *   **Пользователи (User):** Люди (например, `jane@example.com`).
    *   **Группы (Group):** Коллекции пользователей (например, `dev-team`).
    *   **Сервисные аккаунты (ServiceAccount):** Учетные записи, используемые приложениями и подами внутри кластера (например, `default:frontend-sa`).

2.  **Роли (Roles) и Кластерные роли (ClusterRoles):** Что можно делать.
    *   **Роль (Role):** Определяет набор прав (глаголов: `get`, `list`, `create`, `delete`) на определенные ресурсы (например, `pods`, `services`) в рамках одного namespace.
    *   **Кластерная роль (ClusterRole):** Аналогична Роли, но применяется на уровне всего кластера (например, управление `nodes`, `persistentvolumes`).

3.  **Привязки (RoleBindings) и Кластерные привязки (ClusterRoleBindings):** Кто может что делать.
    *   **Привязка (RoleBinding):** Связывает субъект (пользователя, группу, сервисный аккаунт) с Ролью в определенном namespace.
    *   **Кластерная привязка (ClusterRoleBinding):** Связывает субъект с Кластерной ролью для всего кластера.

#### **Часть 3: Практический пример: Ограничение доступа к production**

Цель: Дать разработчику (через сервисный аккаунт) доступ только на чтение к подам и сервисам в namespace `production`.

1.  **Создать Роль:**
    ```yaml
    # role-reader.yaml
    apiVersion: rbac.authorization.k8s.io/v1
    kind: Role
    metadata:
      namespace: production
      name: pod-reader
    rules:
    - apiGroups: [""] # "" указывает на core API group
      resources: ["pods", "services"]
      verbs: ["get", "list", "watch"]
    ```
    Эта роль позволяет получать, перечислять и отслеживать изменения подов и сервисов.

2.  **Создать Привязку:**
    ```yaml
    # rolebinding-reader.yaml
    apiVersion: rbac.authorization.k8s.io/v1
    kind: RoleBinding
    metadata:
      name: read-pods
      namespace: production
    subjects:
    - kind: ServiceAccount
      name: dev-sa # Имя сервисного аккаунта
      namespace: default # Namespace, где находится сервисный аккаунт
    roleRef:
      kind: Role
      name: pod-reader
      apiGroup: rbac.authorization.k8s.io
    ```
    Эта привязка связывает сервисный аккаунт `dev-sa` из namespace `default` с ролью `pod-reader` в namespace `production`.

3.  **Применить конфигурацию:**
    ```bash
    kubectl apply -f role-reader.yaml
    kubectl apply -f rolebinding-reader.yaml
    ```

4.  **Проверить доступ:**
    ```bash
    # Проверяем, может ли сервисный аккаунт 'dev-sa' читать поды
    kubectl auth can-i get pods -n production --as=system:serviceaccount:default:dev-sa
    # Ожидаемый ответ: yes
    
    # Проверяем, может ли он создать под
    kubectl auth can-i create pods -n production --as=system:serviceaccount:default:dev-sa
    # Ожидаемый ответ: no
    ```

#### **Часть 4: Лучшие практики (Best Practices)**

1.  **Используйте группы, а не отдельных пользователей:** Вместо создания `RoleBinding` для каждого пользователя, создайте его для группы (например, `dev-team`). Это упрощает управление.
    *   **Источник:** `Boorshtein Marc, Surovich Scott - Kubernetes An Enterprise Guide`

2.  **Избегайте использования `cluster-admin`:** Эта роль предоставляет полный контроль над кластером. Никогда не давайте ее обычным разработчикам.
    *   **Источник:** `Stencel Grzegorz, Berton Luca - Kubernetes Recipes - 2025`

3.  **Создавайте отдельные сервисные аккаунты для приложений:** Не используйте `default` сервисный аккаунт. Создавайте специальный SA для каждого приложения и настраивайте для него минимальные права.
    *   **Источник:** `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices`

4.  **Используйте `kubectl auth can-i` и `kubectl who-can`:** Регулярно проверяйте права доступа.
    *   `auth can-i`: "Могу ли *я* сделать это?"
    *   `who-can`: "Кто может сделать это?" (требует установки `krew`).
    *   **Источник:** открытых источников

#### **Чек-лист: Настройка RBAC**

| Этап                     | Действие                                                                                               |
|:------------------------ |:------------------------------------------------------------------------------------------------------ |
| **1. Планирование**      | Определите роли (dev, ops, qa) и их права.                                                             |
| **2. Создание SA**       | Создайте отдельные сервисные аккаунты для каждого приложения.                                          |
| **3. Создание ролей**    | Создайте `Role` или `ClusterRole` с минимальными необходимыми правами.                                 |
| **4. Создание привязок** | Свяжите субъекты (пользователи, группы, SA) с ролями с помощью `RoleBinding` или `ClusterRoleBinding`. |
| **5. Проверка**          | Используйте `kubectl auth can-i` для проверки прав.                                                    |

#### **Заключение**

RBAC — это мощный и гибкий механизм, который позволяет вам точно контролировать доступ к вашему кластеру. Начните с простых ролей для чтения и постепенно расширяйте их по мере необходимости. Как указано в `Burns B., Beda J., Hightower K., and Evenson L. - Kubernetes. Up and Running`, лучшая практика — настраивать RBAC как можно раньше. В следующей статье мы рассмотрим, как контролировать трафик между подами с помощью `NetworkPolicy`.
