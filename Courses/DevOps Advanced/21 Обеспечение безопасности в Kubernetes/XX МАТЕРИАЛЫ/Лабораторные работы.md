Вот подборка лабораторных работ по теме "Обеспечение безопасности в Kubernetes: Путь от конфигурации к автономной защите (2025)", разработанных на основе целей занятия и доступных источников.

### **Лабораторная работа 1: Настройка и применение RBAC**

**Цель:** Настроить систему управления доступом на основе ролей для ограничения прав разработчика.

**Задачи:**
1.  Создать namespace `dev-team`.
2.  Создать сервисный аккаунт `frontend-sa` в этом namespace.
3.  Создать `Role`, разрешающий только `get`, `list`, `watch` для `pods` и `services`.
4.  Создать `RoleBinding`, связывающее `frontend-sa` с созданной `Role`.
5.  Проверить права с помощью `kubectl auth can-i` и `kubectl who-can`.

**Инструменты:** `kubectl`
**Источники:** `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices - 2024`, `Бранд А., Ландер Р., Россо Д., Харрис Д. - Kubernetes на практике - 2022`

### **Лабораторная работа 2: Применение Pod Security Standards (PSS)**

**Цель:** Защитить namespace с помощью встроенных политик безопасности Pod.

**Задачи:**
1.  Создать namespace `production`.
2.  Применить политику `baseline` к namespace с помощью аннотаций (`pod-security.kubernetes.io/enforce: baseline`).
3.  Попробовать применить манифест пода, который запускается от `root` (`runAsNonRoot: false`). Убедиться, что создание блокируется.
4.  Исправить манифест, добавив `runAsNonRoot: true`, и применить его.
5.  *(Дополнительно)* Настроить `Kyverno` для принудительного применения более строгой политики `restricted`.

**Инструменты:** `kubectl`, `Kyverno`
**Источники:** `Lapaz Raul - Learning Kubernetes Security, 2nd Edition - 2025`, `Уильям Д. - Kubernetes для разработчиков (Для профессионалов) - 2025`

### **Лабораторная работа 3: Создание и тестирование NetworkPolicy**

**Цель:** Контролировать сетевой трафик между подами.

**Задачи:**
1.  Развернуть два приложения: `frontend` и `database` в одном namespace.
2.  По умолчанию убедиться, что `frontend` может подключиться к `database`.
3.  Создать `NetworkPolicy`, которая **запрещает весь входящий трафик** к `database`.
4.  Проверить, что подключение от `frontend` к `database` теперь заблокировано.
5.  Создать `NetworkPolicy`, которая **разрешает** входящий трафик к `database` только от подов с меткой `app: frontend`.
6.  Убедиться, что соединение восстановилось.

**Инструменты:** `kubectl`, CNI-провайдер с поддержкой NetworkPolicy (Calico, Cilium)
**Источники:** `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices - 2024`, `Бранд А., Ландер Р., Россо Д., Харрис Д. - Kubernetes на практике - 2022`

### **Лабораторная работа 4: Сканирование образов и проверка манифестов**

**Цель:** Обнаружить уязвимости и анти-паттерны на ранних этапах CI/CD.

**Задачи:**
1.  Написать простой Dockerfile для приложения.
2.  С помощью `Trivy` просканировать собранный образ на наличие CVE.
3.  Написать манифест Kubernetes для этого приложения, намеренно добавив анти-паттерн (например, запуск от `root`, отсутствие `resources.limits`).
4.  Проверить манифест с помощью `kube-score` и `polaris`. Проанализировать отчеты.
5.  Исправить манифест и убедиться, что ошибки устранены.

**Инструменты:** `Docker`, `Trivy`, `kube-score`, `polaris`
**Источники:** `Lapaz Raul - Learning Kubernetes Security, 2nd Edition - 2025`, `combined.txt`

### **Лабораторная работа 5: Аудит безопасности кластера и диагностика с помощью eBPF**

**Цель:** Провести аудит конфигурации и диагностировать проблему на уровне ядра.

**Задачи:**
1.  Установить `kube-bench` в кластер.
2.  Запустить аудит и проанализировать отчет. Найти хотя бы одну проблему с конфигурацией.
3.  Создать под, который падает с `CrashLoopBackOff` из-за попытки открыть несуществующий файл.
4.  Установить `inspektor-gadget`.
5.  Использовать команду `kubectl gadget trace open` для диагностики причины падения пода, наблюдая за системными вызовами `openat`.

**Инструменты:** `kube-bench`, `inspektor-gadget`
**Источники:** `Lapaz Raul - Learning Kubernetes Security, 2nd Edition - 2025`, `combined.txt`

### **Лабораторная работа 6: Управление секретами с Sealed Secrets и Vault**

**Цель:** Безопасно хранить чувствительные данные.

**Задачи:**
1.  Установить `Sealed Secrets` в кластер.
2.  Создать обычный `Secret` с паролем от базы данных.
3.  Зашифровать этот `Secret` с помощью `kubeseal`, создав `SealedSecret`.
4.  Сохранить `SealedSecret` в Git-репозиторий (имитация).
5.  Применить `SealedSecret` к кластеру и убедиться, что обычный `Secret` был создан.
6.  *(Дополнительно)* Установить HashiCorp Vault и настроить `vault-agent-injector` для пода.

**Инструменты:** `kubectl`, `kubeseal`, `Sealed Secrets Controller`, HashiCorp Vault
**Источники:** `Gkatziouras Emmanouil, Adams Rom, Xi Chen - Kubernetes Secrets Handbook - 2024`, `Бранд А., Ландер Р., Россо Д., Харрис Д. - Kubernetes на практике - 2022`

### **Лабораторная работа 8: Внедрение политик безопасности с Kyverno**

**Цель:** Автоматически блокировать небезопасные конфигурации.

**Задачи:**
1.  Установить `Kyverno` в кластер.
2.  Создать политику `ClusterPolicy`, которая **запрещает** создание подов с `privileged: true`.
3.  Попробовать применить манифест пода с привилегированным контейнером. Убедиться, что создание блокируется.
4.  Создать политику, которая **автоматически добавляет** лимиты ресурсов (`resources.limits.cpu: 500m`) к подам, если они не указаны.
5.  Применить манифест без лимитов и убедиться, что они были добавлены автоматически.

**Инструменты:** `kubectl`, `Kyverno`
**Источники:** `combined.txt`, `Chowdhury Soumiyajit Das - Mastering DevOps in Kubernetes - 2024`
