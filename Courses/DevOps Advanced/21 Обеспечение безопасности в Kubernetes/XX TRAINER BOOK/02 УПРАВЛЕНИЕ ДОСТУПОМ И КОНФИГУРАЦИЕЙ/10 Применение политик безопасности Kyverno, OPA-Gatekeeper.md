### **Статья 10: Применение политик безопасности: `Kyverno`, `OPA/Gatekeeper`**

#### **Введение**

Представьте, что разработчик случайно развернул под с `runAsNonRoot: false`, что создает серьезную уязвимость. Без политики этот под будет запущен. `Kyverno` и `OPA/Gatekeeper` — это "стражи ворот" вашего кластера. Они проверяют каждый манифест перед его применением и могут автоматически блокировать или исправлять опасные конфигурации. Как указано в `Lapaz Raul - Learning Kubernetes Security, 2nd Edition`, автоматизация политик — это следующий шаг после ручной проверки.

#### **Что такое Policy Engine?**

Policy Engine — это система, которая применяет набор правил (политик) к ресурсам Kubernetes. Он работает как **Admission Controller**, перехватывая запросы API (create, update) и проверяя их на соответствие политикам.

*   **Режимы работы:**
    *   **Audit (аудит):** Политика проверяет объект и записывает нарушение в журнал, но не блокирует создание.
    *   **Enforce (принудительное применение):** Политика блокирует создание объекта, если он нарушает правила.
    *   **Mutate (изменение):** Политика автоматически изменяет объект, чтобы он соответствовал правилам (например, добавляет `resources.requests`).

#### **`Kyverno`: Простота и удобство**

`Kyverno` — это проект CNCF, созданный специально для Kubernetes.

*   **Архитектура:** Работает как Kubernetes Operator. Политики определяются как Custom Resource Definitions (CRD).
*   **Преимущества:**
    *   **Простота:** Политики пишутся на привычном YAML, что делает их легко читаемыми и понятными для всех, кто работает с Kubernetes.
    *   **Интеграция:** Глубоко интегрирован в экосистему Kubernetes.
    *   **Легковесность:** Относительно небольшой по размеру и потреблению ресурсов.
*   **Недостатки:** Менее гибкий по сравнению с OPA для очень сложных логических правил.

#### **`OPA/Gatekeeper`: Мощность и гибкость**

`OPA` (Open Policy Agent) — это универсальный движок политик, а `Gatekeeper` — это его адаптация для Kubernetes.

*   **Архитектура:** `OPA` использует собственный декларативный язык **Rego** для написания политик.
*   **Преимущества:**
    *   **Гибкость:** Язык Rego позволяет писать очень сложные, условные политики, которые невозможно выразить на YAML.
    *   **Универсальность:** OPA можно использовать не только для Kubernetes, но и для проверки конфигураций Terraform, CI/CD и других систем.
*   **Недостатки:** Язык Rego требует изучения, что усложняет его использование для новичков.

#### **Практический пример с `Kyverno`**

1.  **Установка `Kyverno`:**
    ```bash
    kubectl apply -f https://github.com/kyverno/kyverno/releases/download/v1.11.1/install.yaml
    ```

2.  **Создание политики:**
    Сохраните пример политики из слайда в файл `disallow-root.yaml`.

3.  **Применение политики:**
    ```bash
    kubectl apply -f disallow-root.yaml
    ```

4.  **Тестирование:**
    Попробуйте применить манифест пода, где `runAsNonRoot: false`. `Kyverno` заблокирует его и вернет ошибку с сообщением: "Running as root is not allowed."

#### **Заключение**

`Kyverno` и `OPA/Gatekeeper` — это мощные инструменты для автоматизации безопасности. `Kyverno` идеален для команд, которые ценят простоту и быстрое внедрение. `OPA/Gatekeeper` — выбор для тех, кому нужна максимальная гибкость. Оба инструмента позволяют внедрить практику "Shift-Left Security", блокируя уязвимости на этапе деплоя. В следующей статье мы перейдем к безопасности на этапе разработки.
