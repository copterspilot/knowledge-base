### **Статья 8: Сетевые политики (NetworkPolicy): Контроль трафика между подами**

#### **Введение**

Представьте, что злоумышленник проник в ваш под с фронтендом. По умолчанию этот под может подключиться к любому сервису в кластере, включая базу данных. `NetworkPolicy` — это ваш "сетевой брандмауэр" на уровне подов. Он позволяет явно разрешать или запрещать трафик, ограничивая "зону перемещения" (lateral movement) атакующего. Как указано в `Бранд А., Ландер Р., Россо Д., Харрис Д. - Kubernetes на практике`, это ключевой элемент принципа минимальных привилегий в сети.

#### **Что такое NetworkPolicy?**

`NetworkPolicy` — это объект Kubernetes API, который определяет правила для входящего (`ingress`) и исходящего (`egress`) трафика между подами.

*   **Важно:** `NetworkPolicy` не работает сама по себе. Она требует **CNI-провайдера**, который ее поддерживает (например, Calico, Cilium, Weave Net). Без такого провайдера объекты `NetworkPolicy` будут проигнорированы.

#### **Принцип "по умолчанию разрешено, явно запрещено"**

По умолчанию в Kubernetes действует политика "всё разрешено": любой под может инициировать соединение с любым другим подом.

*   **`NetworkPolicy` применяется как "белый список":** Вы создаете политику, которая разрешает только определенный трафик, и все остальное по умолчанию блокируется.
*   **Или как "черный список":** Вы создаете политику, которая явно запрещает определенный трафик.

#### **Ключевые компоненты NetworkPolicy**

1.  **`podSelector`:**
    *   Определяет, к каким подам применяется эта политика.
    *   Использует метки (labels) для выбора подов.
    *   `podSelector: {}` выбирает **все** поды в namespace.

2.  **`ingress`:**
    *   Список правил для **входящего** трафика (кто может подключаться к выбранным подам).
    *   Каждое правило может содержать:
        *   `from`: Источники трафика (другие поды, namespace, IP-блоки).
        *   `ports`: Порты и протоколы, на которые разрешено подключаться.

3.  **`egress`:**
    *   Список правил для **исходящего** трафика (куда могут подключаться выбранные поды).
    *   Каждое правило может содержать:
        *   `to`: Назначения трафика.
        *   `ports`: Порты и протоколы, к которым разрешено подключаться.

4.  **`policyTypes`:**
    *   Опциональное поле, которое явно указывает, применяется ли политика к `Ingress`, `Egress` или к обоим. Если не указано, типы определяются наличием соответствующих секций.

#### **Практические примеры**

1.  **Запретить весь входящий трафик:**
    ```yaml
    # deny-all-ingress.yaml
    kind: NetworkPolicy
    apiVersion: networking.k8s.io/v1
    metadata:
      name: deny-all-ingress
      namespace: production
    spec:
      podSelector: {}
      policyTypes:
      - Ingress
    ```
    Эта политика блокирует **весь** входящий трафик ко **всем** подам в namespace `production`. После ее применения нужно создать другие политики, которые явно разрешат необходимый трафик (например, от ingress-контроллера к фронтенду).

2.  **Разрешить трафик только от определенного сервиса:**
    ```yaml
    # allow-frontend-to-db.yaml
    kind: NetworkPolicy
    apiVersion: networking.k8s.io/v1
    metadata:
      name: allow-frontend-to-db
    spec:
      podSelector:
        matchLabels:
          app: database
      ingress:
      - from:
        - podSelector:
            matchLabels:
              app: frontend
        ports:
        - protocol: TCP
          port: 5432
    ```
    Эта политика разрешает входящие TCP-соединения на порт 5432 только от подов с меткой `app=frontend` к подам с меткой `app=database`.

#### **Заключение**

`NetworkPolicy` — это мощный инструмент для повышения безопасности кластера. Он позволяет реализовать принцип "глубокой защиты", ограничивая возможности атакующего в случае компрометации одного из подов. В следующей статье мы рассмотрим `Pod Security Standards`, которые заменили устаревшие Pod Security Policies.
