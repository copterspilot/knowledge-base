### **Статья 11: Политики безопасности Pod (Pod Security Standards): Современная замена PSP**

#### **Введение**

В старых версиях Kubernetes существовали Pod Security Policies (PSP) — мощный, но чрезвычайно сложный механизм для контроля безопасности подов. Однако из-за своей сложности и проблем с масштабированием, PSP были объявлены устаревшими и удалены из Kubernetes начиная с версии 1.25. На их место пришли **Pod Security Standards (PSS)**. Это не отдельный контроллер, а набор **встроенных, упрощенных политик**, которые легче внедрить и поддерживать. Как указано в `Lapaz Raul - Learning Kubernetes Security, 2nd Edition`, PSS — это современный стандарт для обеспечения безопасности на уровне пода.

#### **Проблема: Устаревшие Pod Security Policies (PSP)**

PSP позволяли детально контролировать поведение подов (например, запуск от root, использование привилегированных контейнеров). Однако их использование было сопряжено со значительными трудностями:
*   **Сложность настройки:** Требовалось создавать и управлять множеством объектов.
*   **Сложность отладки:** Ошибки в конфигурации PSP были трудно диагностируемы.
*   **Производительность:** PSP работали как Admission Controller и могли замедлять создание подов.

#### **Решение: Pod Security Standards (PSS)**

Pod Security Standards — это рекомендации от Kubernetes Security Working Group, которые были интегрированы в ядро Kubernetes. Они определяют три предопределенных уровня безопасности, которые можно применить к namespace.

*   **`privileged` (привилегированный):**
    *   **Описание:** Никаких ограничений. Поды могут делать всё, что им угодно.
    *   **Использование:** Только для системных namespace (`kube-system`).

*   **`baseline` (базовый):**
    *   **Описание:** Запрещает явно опасные практики, но не мешает большинству приложений работать.
    *   **Примеры запрещенных действий:**
        *   Запуск контейнеров от имени `root` (если не указано `runAsNonRoot: false`).
        *   Использование привилегированных контейнеров (`privileged: true`).
        *   Монтирование чувствительных хост-директорий (например, `/proc`).
    *   **Использование:** Подходит для большинства production-приложений.

*   **`restricted` (ограниченный):**
    *   **Описание:** Самый строгий уровень, соответствующий рекомендациям CIS (Center for Internet Security).
    *   **Примеры требований:**
        *   Обязательное использование `runAsNonRoot: true`.
        *   Обязательная установка `readOnlyRootFilesystem: true`.
        *   Строгие ограничения на `capabilities`.
    *   **Использование:** Рекомендуется для максимально безопасной среды.

#### **Применение политик**

1.  **Через метки namespace (встроенный способ):**
    Вы можете применить уровень безопасности к namespace с помощью специальных аннотаций.
    ```yaml
    # namespace.yaml
    apiVersion: v1
    kind: Namespace
    metadata:
      name: production
      labels:
        # Принудительное применение baseline политики
        pod-security.kubernetes.io/enforce: baseline
        # Аудит (предупреждение, но не блокировка)
        pod-security.kubernetes.io/audit: restricted
        # Действие при нарушении (send warning)
        pod-security.kubernetes.io/warn: restricted
    ```
    *   `enforce`: Принудительное применение политики.
    *   `audit`: Проверка на нарушение (логирование).
    *   `warn`: Отправка предупреждения при нарушении.

2.  **Через `Kyverno` или `OPA/Gatekeeper` (рекомендуемый способ):**
    Хотя PSS встроены, многие команды предпочитают использовать `Kyverno` или `OPA/Gatekeeper` для их применения. Это позволяет:
    *   Использовать более сложные логические правила.
    *   Получать более информативные сообщения об ошибках.
    *   Интегрировать с существующими системами управления политиками.

#### **Заключение**

Pod Security Standards — это современная, встроенная альтернатива устаревшим PSP. Они значительно упрощают обеспечение базовой безопасности на уровне подов. Начните с применения уровня `baseline` к своим production-namespace и постепенно переходите к `restricted`. В следующей статье мы рассмотрим, как применять эти и другие политики с помощью `Kyverno` и `OPA/Gatekeeper`.
