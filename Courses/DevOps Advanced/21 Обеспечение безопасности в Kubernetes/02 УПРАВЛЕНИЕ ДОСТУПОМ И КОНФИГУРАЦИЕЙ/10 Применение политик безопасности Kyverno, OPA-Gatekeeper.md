## [10] Применение политик безопасности: `Kyverno`, `OPA/Gatekeeper`

**Содержимое слайда (для PowerPoint):**
-   **Заголовок:** Применение политик безопасности: `Kyverno`, `OPA/Gatekeeper`
-   **Основной текст / список:**
    *   **Что это:** Адмит-контроллеры для принудительного применения политик безопасности и управления конфигурацией.
    *   **`Kyverno`:** Политики на YAML. Простота для типичных задач (e.g., "все образы из `registry.company.com`").
    *   **`OPA/Gatekeeper`:** Политики на Rego. Максимальная гибкость для сложных сценариев.
    *   **Пример `Kyverno` (запрет публичных образов):**
        _yaml
        apiVersion: kyverno.io/v1
        kind: ClusterPolicy
        meta
          name: disallow-public-images
        spec:
          validationFailureAction: enforce
          rules:
          - name: validate-image-registry
            match:
              resources:
                kinds: [Pod, Deployment]
            validate:
              message: "Использование образов из публичных реестров запрещено."
              pattern:
                spec:
                  containers:
                  - image: "!docker.io/*"_
-   **Дополнительная информация (внизу):** "Автоматизация безопасности: превращаем best practices в железные правила."

#### **1. Описание визуального оформления**
Слайд должен содержать два столбца: слева — `Kyverno` (иконка YAML, простая схема), справа — `OPA/Gatekeeper` (иконка Rego, сложная схема). В центре — логотип Kubernetes с иконкой щита. Нижняя часть слайда — пример манифеста `Kyverno`, выделенный цветным блоком.

#### **2. Ключевые тезисы**
*   Адмит-контроллеры — это "стражи у ворот" кластера, проверяющие каждый запрос.
*   `Kyverno` — идеален для DevOps-инженеров благодаря простому YAML.
*   `OPA/Gatekeeper` — мощный инструмент для сложных, кастомных политик.

#### **3. Описание для выступающего (речь)**
"Мы научились проверять и настраивать безопасность вручную. А что, если мы можем автоматизировать этот процесс? Для этого существуют адмит-контроллеры. Они проверяют каждый объект, который вы пытаетесь создать в кластере, и могут его отклонить, если он нарушает политику. Например, с помощью `Kyverno` мы можем написать правило, которое блокирует деплоймент любого образа из `docker.io`. Как указано в `Boorshtein Marc, Surovich Scott - Kubernetes An Enterprise Guide`, эти инструменты являются ключевыми для обеспечения compliance в корпоративных средах."

#### **6. Типовые вопросы и ответы (Q&A):**
*   **В:** Какой инструмент выбрать: `Kyverno` или `OPA/Gatekeeper`?
    *   **О:** Начните с `Kyverno` для простых задач. Используйте `OPA/Gatekeeper`, если вам нужна максимальная гибкость и вы готовы работать с языком Rego.
*   **В:** Могут ли политики нарушить работу кластера?
    *   **О:** Да, особенно на уровне кластера. Всегда тестируйте политики в staging-среде и используйте `validationFailureAction: audit` для начала.

#### **7. Примеры использования / Типовые сценарии**
*   **Обеспечение compliance:** Запретить деплойменты без обязательных аннотаций (например, `team: <имя>`).
*   **Безопасность образов:** Блокировать образы, не прошедшие сканирование или не имеющие подписи.
*   **Управление конфигурацией:** Автоматически добавлять `resources.limits` ко всем подам, если они не указаны.

### **Таблица сравнения `Kyverno` и `OPA/Gatekeeper`**

| Критерий                       | **Kyverno**                                                                                                                                   | **OPA/Gatekeeper**                                                                                                                 |
|:------------------------------ |:--------------------------------------------------------------------------------------------------------------------------------------------- |:---------------------------------------------------------------------------------------------------------------------------------- |
| **Язык для написания политик** | **YAML.** Политики пишутся на том же языке, что и манифесты Kubernetes. Это делает их понятными и легко проверяемыми.                         | **Rego.** Специализированный декларативный язык запросов, основанный на Datalog. Более мощный, но требует изучения.                |
| **Сложность освоения**         | **Низкая.** Идеален для команд, которые уже знакомы с Kubernetes.                                                                             | **Высокая.** Требует изучения нового языка (Rego) и концепций OPA.                                                                 |
| **Тип инструмента**            | **Специализированный движок политик для Kubernetes.** Создан специально для Kubernetes и его API.                                             | **Универсальный движок политик (OPA), адаптированный для Kubernetes (Gatekeeper).** OPA — это общая система управления политиками. |
| **Возможности**                | Поддерживает **валидацию**, **мутацию** (изменение) и **генерацию** ресурсов.                                                                 | Поддерживает **валидацию** и **аудит**. Мутация и генерация возможны, но требуют более сложных политик.                            |
| **Архитектура**                | Упрощенная, "нативная для Kubernetes". Gatekeeper не нужен.                                                                                   | Gatekeeper действует как "мост" между OPA и Kubernetes. OPA встроен в Gatekeeper.                                                  |
| **Интеграция с GitOps**        | **Отличная.** Политики — это обычные объекты Kubernetes (Custom Resource), которые легко хранить и управлять через Git.                       | **Хорошая.** Политики (ConstraintTemplates и Constraints) также являются объектами Kubernetes.                                     |
| **Гибкость**                   | **Средняя.** Отлично подходит для большинства сценариев безопасности и compliance в Kubernetes. Может быть ограничен для очень сложных логик. | **Очень высокая.** Язык Rego позволяет создавать чрезвычайно сложные и условные политики.                                          |
| **Производительность**         | Обычно хорошая.                                                                                                                               | Может быть выше из-за оптимизаций OPA, но зависит от сложности политик на Rego.                                                    |
| **Поддержка и сообщество**     | Быстро растущее сообщество, проект CNCF (инкубационный). Популярен на GitHub.                                                                 | Зрелое решение с большим сообществом. OPA — проект CNCF (градуированный).                                                          |
| **Идеальный сценарий**         | Команды, которым нужен простой, быстрый и надежный способ внедрения политик безопасности и best practices.                                    | Команды, которым нужна максимальная гибкость и готовые к изучению Rego для реализации сложных, уникальных политик.                 |
| **Источники**                  | `Бранд А., Ландер Р., Россо Д., Харрис Д. - Kubernetes на практике`, `Sayfan Gigi - Mastering Kubernetes, 4th Edition`                        | `Boorshtein Marc, Surovich Scott - Kubernetes An Enterprise Guide`, `Kubernetes Изнутри`                                           |
