## [7] `kubectl who-can`: Визуализация прав доступа

**Содержимое слайда (для PowerPoint):**
-   **Заголовок:** `kubectl who-can`: Визуализация прав доступа
-   **Основной текст / список:**
    *   **Что делает:** Показывает, **кто** (пользователи, сервисные аккаунты) может выполнить **определенное действие** (например, `create pods`).
    *   **Установка:** `kubectl krew install who-can`
    *   **Синтаксис:** `kubectl who-can <действие> <ресурс> [--namespace <имя>]`
    *   **Пример:**
        _bash
        kubectl who-can create pods --namespace production
        # USER           SERVICEACCOUNT
        # alice@corp.com default:alice-sa
        # dev-team       dev:dev-sa_
-   **Дополнительная информация (внизу):** "Безопасность — это прозрачность. Вы должны знать, кто что может делать."

#### **Уровень сложности**
Средний

#### **Цель слайда**
Представить аудитории плагин `kubectl-who-can` как мощный инструмент для визуализации и аудита системы RBAC. Научить выявлять избыточные привилегии и расследовать инциденты.

#### **1. Описание визуального оформления**
Слайд должен контрастировать с предыдущим. Слева — команда `kubectl auth can-i` (вопрос "Я могу?"), справа — команда `kubectl who-can` (вопрос "Кто может?"). Используйте схему с иконками пользователей и сервисных аккаунтов, стрелки от них к ресурсу "Pods". Внизу — ключевая фраза о прозрачности.

#### **2. Ключевые тезисы**
*   `kubectl who-can` — это "детектор" избыточных привилегий.
*   Он позволяет проводить аудит безопасности, отвечая на вопрос "Кто может выполнить это действие?".
*   Это критически важный инструмент для расследования инцидентов и управления доступом.

#### **3. Описание для выступающего (речь)**
"Мы научились проверять права для одного пользователя с помощью `auth can-i`. А что, если мы хотим узнать, кто в нашей команде имеет права на создание подов в production? Нам придется проверить каждого по отдельности? Нет. Для этого есть плагин `kubectl-who-can`. Он анализирует все `RoleBinding`, `ClusterRoleBinding` и `Roles` в кластере и выдает список всех субъектов, которые имеют указанное право. Как написано в `Sachdeva Piyush - Certified Kubernetes Administrator Study Companion`, понимание полной картины доступа — это ключ к безопасному кластеру."

#### **4. Демо-сценарий (если уместен)**
*   **Демо:** Показать команду `kubectl who-can create pods --namespace default`. Затем создать новую `RoleBinding` и повторить команду, чтобы показать, как список субъектов изменился.

#### **5. Связь с прошлыми материалами:**
*   Прямая связь с Слайдом 5 и 6: Развивает тему RBAC, переходя от односторонней проверки (`can-i`) к полной визуализации (`who-can`).
*   Подготавливает к теме аудита безопасности (`kube-bench`).

#### **6. Типовые вопросы и ответы (Q&A):**
*   **В:** Нужно ли устанавливать `krew` для `who-can`?
    *   **О:** Да, `krew` — это менеджер плагинов. Сначала установите `krew`, а затем `kubectl krew install who-can`.
*   **В:** Можно ли использовать `who-can` для проверки прав на уровне всего кластера?
    *   **О:** Да, просто не указывайте флаг `--namespace`, и команда будет проверять `ClusterRoleBinding`.

#### **7. Примеры использования / Типовые сценарии**
*   **Аудит безопасности:** Регулярно проверять, кто имеет права на критически важные операции (например, `delete nodes`).
*   **Расследование инцидентов:** Если был создан вредоносный под, использовать `who-can`, чтобы найти всех потенциальных подозреваемых.
*   **Управление доступом:** Перед изменением политик безопасности убедиться, кто будет затронут.
