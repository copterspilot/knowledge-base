### **18 Аудит кластера и Compliance**

**1. Визуальный ряд:**
*   Инфографика "Жизненный цикл аудита": Планирование -> Сбор данных -> Анализ -> Отчет -> Действия
*   Сравнительная таблица инструментов аудита:
   
| Инструмент             | Фокус               | Метод сбора           | Отчетность  |
| ---------------------- | ------------------- | --------------------- | ----------- |
| **kube-bench**         | CIS Benchmark       | SSH/API               | JSON, JUnit |
| **kube-hunter**        | Penetration testing | Активное сканирование | HTML, PDF   |
| **kube-audit**         | Audit logs          | API Server logs       | Логи        |
| **Fairwinds Insights** | Комплексный         | Агент                 | Дашборд     |
   
*   Пример отчета kube-bench с FAIL/WARN/PASS
*   Скриншот дашборда Fairwinds Insights или аналогичного решения
*   Схема интеграции с SIEM системами (Splunk, Elastic)

**2. Демо-сценарий:**
*   Запуск аудита в реальном времени:
    ```bash
    # Запуск CIS Benchmark проверки
    kube-bench --benchmark cis-1.8 run --json > audit-report.json
    
    # Запуск penetration тестов
    kube-hunter --remote <cluster-ip> --report pdf
    
    # Просмотр audit логов
    kubectl get events --sort-by='.lastTimestamp' -A | tail -20
    ```
*   Показать разницу между различными типами аудита

**3. Ключевые тезисы:**
*   "kube-bench — стандарт для проверки соответствия CIS Benchmark"
*   "kube-hunter — поиск уязвимостей 'глазами хакера'"
*   "Аудит — не разовое событие, а непрерывный процесс"
*   "Интегрируйте аудит в CI/CD для непрерывного compliance"
*   "Отчеты должны вести к действиям: фиксам и улучшениям"

**4. Описание для выступающего:**
Подчеркнуть важность регулярного аудита не как формальности, а как инструмента улучшения безопасности. Показать как превращать отчеты в actionable задачи. Важно объяснить разницу между различными типами аудита.

**5. Связь с прошлыми материалами:**
*   Завершение цикла "Shift-Left -> Политики -> Аудит"
*   Использование инструментов из предыдущих слайдов для исправления найденных проблем
*   Интеграция с мониторингом и оповещениями

**6. Типовые вопросы и ответы (Q&A):**
*   **В:** Как часто проводить аудит?
    *   **О:** CIS Benchmark — после изменений инфраструктуры, kube-hunter — ежеквартально
*   **В:** Что делать с FAIL в kube-bench?
    *   **О:** Приоритизировать по риску, начинать с критичных для безопасности
*   **В:** Нужен ли внешний аудит?
    *   **О:** Для compliance часто требуется независимый аудит третьей стороной

**7. Типовые примеры/сценарии:**
*   **Сценарий 1:** Подготовка к SOC2 сертификации
    *   Регулярный kube-bench + исправление нарушений
    *   Documented процессы реагирования на инциденты
    
*   **Сценарий 2:** Реакция на новую CVE
    *   Запуск целевого аудита на наличие уязвимости
    *   Экстренный патчинг или mitigation
