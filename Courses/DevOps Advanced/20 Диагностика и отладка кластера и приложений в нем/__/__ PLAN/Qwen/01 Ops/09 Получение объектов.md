### **Слайд 9: Получение объектов - `kubectl get`**

*   **Заголовок:** Получение объектов - `kubectl get`
*   **Ключевые элементы (примерный вид слайда):**
    *   Скриншот терминала: `kubectl get pods,services`
    *   Скриншот терминала: `kubectl get events --watch`
    *   Скриншот терминала: `kubectl get deployment my-deploy -o yaml`
    *   Иконки различных ресурсов K8s (Pod, Service, Deployment).

---

*   **Описание (для выступающего / Расширенное описание темы):**
    *   **Цель слайда:** Представить команду `kubectl get` как базовый инструмент для получения списка объектов Kubernetes и экспорта их конфигурации. Подчеркнуть её универсальность и важность для мониторинга состояния кластера.
    *   **Ключевое сообщение:** Команда `kubectl get` является фундаментальной для получения информации о ресурсах в кластере. Она позволяет быстро получить список объектов определенного типа (или нескольких типов), отфильтровать их, отформатировать вывод и даже экспортировать полную спецификацию ресурса в формате YAML или JSON. Особенно полезна для мониторинга событий (`events`) в реальном времени.
    *   **Основные тезисы:**
        *   `kubectl get <тип_ресурса>` - базовое использование для получения списка ресурсов.
        *   **Множественные типы:** Можно указать несколько типов: `kubectl get pods,services,deployments`.
        *   **Формат вывода:** `-o wide` (дополнительные колонки), `-o yaml`, `-o json` (для экспорта манифестов), `-o name` (только имена).
        *   **Фильтрация:** `--selector <label-selector>` (по меткам), `--field-selector` (по полям, например `status.phase=Running`).
        *   **Мониторинг:** `kubectl get events --watch` (или `-w`) - непрерывно отслеживает новые события в кластере. *(Из субтитров 2019, PDF 2019)*
        *   **Экспорт манифестов:** `kubectl get <тип>/<имя> -o yaml` - получает текущую конфигурацию объекта из API-сервера в виде YAML. Полезно для редактирования и повторного применения или для анализа. *(Из субтитров 2019, PDF 2019)*
        *   `get` показывает состояние "по запросу". Для подробной информации и событий используйте `describe`.
    *   *(Из PDF 2019, слайд 4.7)* "get events--watch- посмотреть за event-объектами в кластере(изменения состояний объектов, фейлы проверок и т.п.) get type/name-o yaml- получить YAML с объектом из Kubernetes, если вдруг его потеряли, создали оператором или вручную и т.п."
    *   *(Из субтитров 2019)* "Kubectl get для дебага интересно несколько вещей, то есть kubectl events-watch — это посмотреть за ивент-объектами в кластере, это изменения, которые сопровождают жизненный цикл каких-то объектов... Можно ставить различные расширялки... То есть это не совсем лог, это такой общий список событий в кластере, что у нас творится. И куб КТО GetTypeInName. Он позволяет в виде ямлика получить какой-то наш типущий объект из кубернетис-кластера... Смотреть ямовую спецификацию, можно почистить ее потом от мусора и положить в репозиторий."
    *   *(Из чата 2019)* "показать, как выглядят ивенты в кластере... можно посмотреть все ивенты по всем наимспейсам... видно, что происходит какое-то убийство контейнеров... можно, соответственно, понаблюдать... можно сделать команду watch only, которая просто покажет последние события". *(Демонстрирует использование `get events --watch`)*

*   **Типовые вопросы и ответы по теме слайда:**
    *   **В:** В чем разница между `kubectl get pods` и `kubectl get events`?
    *   **О:** `kubectl get pods` показывает список подов и их текущее состояние (Running, Pending и т.д.). `kubectl get events` показывает журнал событий кластера, связанных с различными объектами (создание подов, ошибки планировщика, сбои контейнеров и т.д.). Events дают контекст происходящего.
    *   **В:** Как мне постоянно видеть новые события в кластере?
    *   **О:** Используйте флаг `--watch` или `-w`: `kubectl get events --watch`. Это будет обновлять вывод по мере появления новых событий.
    *   **В:** Зачем экспортировать манифест объекта через `kubectl get <type/name> -o yaml`? Разве у меня нет исходного файла?
    *   **О:** Да, исходный файл может быть. Но `kubectl get -o yaml` показывает *фактическое* состояние объекта в кластере, включая значения по умолчанию, установленные API-сервером, и любые изменения, сделанные операторами или другими процессами. Это полезно для анализа, создания резервных копий или модификации текущего состояния.
    *   **В:** Можно ли отфильтровать поды, например, только запущенные?
    *   **О:** Да, с помощью `--field-selector`. Например: `kubectl get pods --field-selector status.phase=Running`. Для фильтрации по меткам используйте `--selector` или `-l`: `kubectl get pods -l app=my-app`.

*   **Примеры использования / Типовые сценарии:**
    *   **Быстрая проверка состояния:** `kubectl get pods -n my-namespace` - проверить, все ли поды работают.
    *   **Мониторинг событий:** `kubectl get events --watch` - следить за происходящим в кластере в реальном времени.
    *   **Экспорт манифеста:** `kubectl get deployment my-app -o yaml > my-app-deployment-backup.yaml` - сделать резервную копию манифеста деплоймента.
    *   **Поиск по меткам:** `kubectl get services -l app=web` - найти все сервисы, относящиеся к веб-приложениям.
    *   *(Из субтитров 2019)* "Можно посмотреть все ивенты по всем наимспейсам... видно, что происходит какое-то убийство контейнеров... можно, соответственно, понаблюдать".

*   **Пример вывода `kubectl get`:**
    *   **`kubectl get pods,services`:**
        ```bash
        $ kubectl get pods,services
        NAME                                READY   STATUS    RESTARTS   AGE
        pod/my-app-7d5b8c9c4-xl2v9          2/2     Running   0          10m
        pod/my-database-5c9b8f7d5c-def34    1/1     Running   0          20m

        NAME                    TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
        service/kubernetes      ClusterIP   10.96.0.1       <none>        443/TCP   5d
        service/my-app-svc      ClusterIP   10.96.5.10      <none>        80/TCP    10m
        service/my-db-svc       ClusterIP   10.96.10.15     <none>        5432/TCP  20m
        ```
    *   **`kubectl get events --watch` (фрагмент):**
        ```bash
        $ kubectl get events --watch
        LAST SEEN   TYPE      REASON              OBJECT                             MESSAGE
        10s         Normal    Scheduled           pod/my-app-7d5b8c9c4-xl2v9         Successfully assigned default/my-app-7d5b8c9c4-xl2v9 to node-1
        9s          Normal    Pulling             pod/my-app-7d5b8c9c4-xl2v9         Pulling image "my-app:v1.2.3"
        5s          Normal    Pulled              pod/my-app-7d5b8c9c4-xl2v9         Successfully pulled image "my-app:v1.2.3"
        5s          Normal    Created             pod/my-app-7d5b8c9c4-xl2v9         Created container my-app
        5s          Normal    Started             pod/my-app-7d5b8c9c4-xl2v9         Started container my-app
        # (Вывод обновляется при новых событиях)
        ```
    *   **`kubectl get deployment my-deploy -o yaml` (фрагмент):**
        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          annotations:
            deployment.kubernetes.io/revision: "1"
          creationTimestamp: "2025-01-03T10:00:00Z"
          generation: 1
          name: my-deploy
          namespace: default
          resourceVersion: "12345"
          uid: a1b2c3d4-e5f6-7890-1234-567890abcdef
        spec:
          progressDeadlineSeconds: 600
          replicas: 3
          revisionHistoryLimit: 10
          selector:
            matchLabels:
              app: my-app
          strategy:
            rollingUpdate:
              maxSurge: 25%
              maxUnavailable: 25%
            type: RollingUpdate
          template:
            metadata:
              labels:
                app: my-app
            spec:
              containers:
              - image: my-app:v1.2.3
                imagePullPolicy: IfNotPresent
                name: my-app
                ports:
                - containerPort: 8080
                  protocol: TCP
                # ... (остальные поля spec)
        status:
          availableReplicas: 3
          conditions:
          # ... (поля status)
        ```
        *   **Объяснение:** Этот вывод показывает полную спецификацию деплоймента, как она хранится в API-сервере. Он включает `metadata`, `spec` (желаемое состояние) и `status` (текущее состояние). Такой вывод можно сохранить в файл, отредактировать и применить снова.
