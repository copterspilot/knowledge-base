**Глубокая диагностика: `kubectl describe` и `kubectl logs`**

---

#### **Описание слайда**

1. **Визуальный ряд**
    - **Примеры команд** с подсветкой синтаксиса:
        
         ```
         kubectl describe pod <pod-name>
         kubectl logs <pod-name> --tail=50
         kubectl logs <pod-name> -c <container-name> --previous
         ```
        
    - **Вывод команд** в виде структурированного текста:
        - Пример вывода `kubectl describe pod` (с разделами: Events, Conditions, Containers).
        - Пример логов из `kubectl logs` (с таймстампами и сообщениями об ошибках).
    - **Схема**:
        - Слева: Под с контейнерами и событиями.
        - Справа: Пример вывода `describe` и `logs`.
    - **Иконки**:
        - 🔍 — для `kubectl describe` (детальный анализ).
        - 📜 — для `kubectl logs` (просмотр логов).
    - **Фон**: Тёмный (для лучшей читаемости терминального вывода).

---

2. **Демо-сценарий** Показать **живой пример**:
    - Выполнить `kubectl describe pod <pod-name>` для анализа событий и состояния пода.
    - Продемонстрировать просмотр логов с помощью:
        
         ```
         kubectl logs <pod-name> --tail=20 --follow
         ```
        
    - Показать, как просмотреть логи предыдущего запуска контейнера:
        
         ```
         kubectl logs <pod-name> --previous
         ```

---

3. **Ключевые тезисы**
    - **`kubectl describe`** — команда для **детального анализа** ресурса:
        - Показывает **конфигурацию**, **события (Events)**, **состояние (Conditions)**.
        - Помогает выявить **ошибки конфигурации**, проблемы с сетью или ресурсами.
    - **`kubectl logs`** — команда для **просмотра логов** контейнеров:
        - Поддерживает фильтрацию по времени (`--since`), количеству строк (`--tail`).
        - Можно просматривать логи **предыдущих запусков** (`--previous`).
        - Полезна для **отладки приложений** и анализа ошибок.
    - Эти команды — **основа глубокой диагностики** в Kubernetes.

---

4. **Описание (для выступающего)**
    - **`kubectl describe`** даёт **полную картину** состояния ресурса, включая события, которые могут указывать на причины проблем.
    - **Events** в выводе `describe` часто содержат **ключевые подсказки** (например, ошибки pull образа или нехватка ресурсов).
    - **`kubectl logs`** позволяет **просматривать логи в реальном времени** (`--follow`), что критично для отладки.
    - Важно объяснить, что **логи могут быть многозадачными** (например, если в поде несколько контейнеров, нужно указывать `--container`).
    - Подчеркнуть, что **сочетание `describe` и `logs`** покрывает **90% случаев диагностики**.

---

5. **Связь с прошлыми материалами**
    - В презентации 2019 года эти команды также рассматривались как ключевые для диагностики.
    - В субтитрах обсуждалось, как **Events в `describe`** помогают выявить причины падения подов.
    - Вопросы из чата:
        - _"Как просмотреть логи для конкретного контейнера в поде?"_ → Использовать флаг `-c <container-name>`.
        - _"Что делать, если логи обрезаются?"_ → Использовать `--tail` для увеличения количества строк или перенаправить логи в файл.

---

6. **Типовые вопросы и ответы (Q&A)**
    - **Вопрос:** _"Как найти причину, если под не запускается?"_ **Ответ:** Использовать `kubectl describe pod` и обратить внимание на раздел **Events**.
    - **Вопрос:** _"Как просмотреть логи, если в поде несколько контейнеров?"_ **Ответ:** Указать имя контейнера: `kubectl logs <pod-name> -c <container-name>`.
    - **Вопрос:** _"Можно ли сохранить логи в файл?"_ **Ответ:** Да: `kubectl logs <pod-name> > pod_logs`.

---

7. **Примеры использования / Типовые сценарии**
    - **Сценарий 1:** Под не запускается из-за ошибки конфигурации. Используем `kubectl describe pod` для анализа **Events**.
    - **Сценарий 2:** Приложение в поде выдаёт ошибки. Смотрим логи в реальном времени: `kubectl logs <pod-name> --follow`.
    - **Сценарий 3:** Нужно проанализировать логи предыдущего запуска контейнера. Используем `kubectl logs <pod-name> --previous`.
