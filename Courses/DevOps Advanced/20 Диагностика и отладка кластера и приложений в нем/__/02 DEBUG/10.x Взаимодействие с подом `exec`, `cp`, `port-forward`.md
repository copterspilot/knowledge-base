**1. Визуальный ряд**
*   Скриншот терминала: `kubectl exec -it my-pod -- sh` (с демонстрацией интерактивной оболочки).
*   Скриншот терминала: `kubectl cp ./local-file my-namespace/my-pod:/app/remote-file`.
*   Скриншот терминала: `kubectl port-forward pod/my-pod 8080:80`.
*   Иконки: терминал (exec), папка со стрелкой (cp), мост (port-forward).

**2. Демо-сценарий (если уместен)**
*   Показать в реальном времени команду `kubectl exec` для входа в контейнер и выполнения простой команды (например, `ls /`).
*   Продемонстрировать `kubectl port-forward` для доступа к веб-интерфейсу, запущенному в поде.

**3. Ключевые тезисы**
*   `kubectl exec` — основной способ выполнения команд внутри контейнера.
*   `kubectl cp` — инструмент для копирования файлов между локальной машиной и контейнером.
*   `kubectl port-forward` — простой способ пробросить порт пода/сервиса на локальную машину.

**4. Описание (для выступающего)**
*   **Цель слайда:** Представить три базовые команды для прямого взаимодействия с подами.
*   **Ключевое сообщение:** Эти команды — ваши "руки и ноги" для диагностики и отладки внутри контейнера.
*   **Основные тезисы:**
    *   **`kubectl exec`:** Позволяет выполнить команду или запустить интерактивную оболочку (с флагами `-it`) внутри контейнера. Это самый прямой способ посмотреть, что происходит внутри пода. *(Из PDF 2019, слайд 4.9)*
    *   **`kubectl cp`:** Позволяет копировать файлы как из пода на локальную машину, так и наоборот. Полезно для извлечения логов, кордампов или обновления конфигурационных файлов. *(Из PDF 2019, слайд 4.9)*
    *   **`kubectl port-forward`:** Создает туннель для доступа к порту пода или сервиса с локальной машины. **Важно:** весь трафик идет через `kube-apiserver`, что делает его непригодным для high-load сценариев. При пробросе до сервиса, трафик направляется только на один конкретный под. *(Из PDF 2019, слайд 4.6)*

**6. Типовые вопросы и ответы (Q&A)**
*   **В:** Почему `kubectl exec` не работает в некоторых образах?
    *   **О:** Потому что в минимальных образах (например, `scratch`, `distroless`) нет стандартной оболочки (`sh`, `bash`). В таких случаях нужно использовать `kubectl debug` для запуска отладочного контейнера. *(Из субтитров 2019: "если у нас так называемый минимальный образ, там никаких шеллов, ничего нам не будет")*.
*   **В:** Можно ли использовать `port-forward` для балансировки нагрузки?
    *   **О:** Нет. `port-forward` пробрасывает трафик только на один конкретный под. Если этот под упадет, туннель разорвется. Это инструмент для диагностики, а не для продакшн-балансировки.
*   **В:** Как скопировать файл из пода, если в нем несколько контейнеров?
    *   **О:** Используйте флаг `-c <container-name>`. Например: `kubectl cp my-namespace/my-pod:/app/log ./log -c my-app-container`.

**7. Примеры использования / Типовые сценарии**
*   **Диагностика:** Использовать `exec` для проверки доступности внутренних сервисов (`curl`, `ping`).
*   **Обновление конфигурации:** Использовать `cp` для замены конфигурационного файла в dev-среде.
*   **Доступ к интерфейсу:** Использовать `port-forward` для доступа к веб-интерфейсу администрирования, запущенному в поде.
