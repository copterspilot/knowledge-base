**`docker.sock`** — это **Unix-сокет** (файл), который является **основным интерфейсом (API)** для взаимодействия с демоном Docker (`dockerd`).

---

### **Как это работает**

1.  **Демон Docker (`dockerd`):** Это фоновый процесс, который управляет контейнерами, образами, сетями и томами на хосте.
2.  **Клиент Docker (`docker`):** Когда вы вводите команду `docker ps` или `docker run`, клиент не выполняет действия сам. Вместо этого он отправляет запрос через файл `docker.sock`.
3.  **`docker.sock`:** Этот файл, обычно расположенный по пути `/var/run/docker.sock`, выступает в роли канала связи. Демон Docker прослушивает этот сокет, получает запросы от клиента и выполняет соответствующие действия.

---

### **Почему это важно в Kubernetes и безопасности**

*   **Доступ к API:** Любой процесс, который имеет доступ к файлу `/var/run/docker.sock`, по сути, получает **полную власть** над Docker-демоном и, следовательно, над хостом, на котором он работает. Это равносильно правам root.
*   **Использование в инструментах:** Некоторые инструменты для диагностики (например, `kubectl debug` в старых версиях) монтировали `docker.sock` внутрь контейнера, чтобы иметь возможность управлять другими контейнерами на той же ноде.
*   **Серьезный риск безопасности:** Если вредоносный контейнер получит доступ к `docker.sock`, он сможет запускать другие контейнеры, получать доступ к файловой системе хоста и полностью скомпрометировать систему.

---

### **Связь с материалами**

> "Агент — это специальный Pod, в который пробрасывается `docker.sock` c хост-системы..."

Это означает, что для выполнения своих функций отладочный агент требовал прямого доступа к API Docker на ноде, что является мощным, но потенциально опасным механизмом.
