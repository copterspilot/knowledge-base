### **07 Итоги: Базовый цикл диагностики инцидента**

**1. Визуальный ряд:**
*   Инфографика с пошаговым алгоритмом диагностики:
    1.  🔍 `kubectl get pods` - Быстрая оценка состояния
    2.  📊 `kubectl top pods` - Анализ потребления ресурсов  
    3.  📋 `kubectl describe pod` - Детальная диагностика
    4.  📝 `kubectl logs` - Анализ работы приложения
    5.  🔧 `kubectl exec` - Непосредственное взаимодействие
*   Схема "Диагностический цикл SRE" с обратной связью
*   Пример вывода команд с выделением ключевых полей для анализа
*   Чек-лист "Что проверять при инциденте" в виде иконок

**2. Демо-сценарий:**
*   Live-демонстрация полного цикла диагностики:
    ```bash
    # Шаг 1: Общая оценка
    kubectl get pods -A | grep -v Running
    
    # Шаг 2: Анализ ресурсов
    kubectl top pods --sort-by=cpu | head -5
    
    # Шаг 3: Детальная диагностика проблемного пода
    kubectl describe pod/<problem-pod>
    
    # Шаг 4: Анализ логов
    kubectl logs <problem-pod> --previous --tail=50
    
    # Шаг 5: Взаимодействие для глубокой диагностики
    kubectl exec -it <problem-pod> -- /bin/sh
    ```
*   Показ как быстро переключаться между командами

**3. Ключевые тезисы:**
*   "Диагностика — это процесс, а не случайные команды. Вырабатывайте системный подход"
*   "Начинайте с общего обзора (`get`), затем углубляйтесь в конкретные проблемы (`describe`, `logs`)"
*   "Сочетание `describe` + `logs` дает 90% ответов о причинах проблем"
*   "Всегда смотрите логи предыдущего запуска (`--previous`) для упавших контейнеров"
*   "Завершайте цикл документацией и предотвращением повторения инцидента"

**4. Описание для выступающего:**
Важно показать методологичность подхода. Объяснить что каждая команда отвечает на конкретный вопрос. Подчеркнуть важность документирования находок и внесения изменений для предотвращения повторных инцидентов (баги, мониторинг, ресурсы).

**5. Связь с прошлыми материалами:**
*   Из чата: "какэтодебажить это прям боль" - показать системный подход
*   Из субтитров: "Базовый цикл диагностики инцидента" - развитие темы
*   Обобщение всех предыдущих команд из слайдов 3-6

**6. Типовые вопросы и ответы (Q&A):**
*   **В:** С чего начать если все пода падают?
    *   **О:** С `kubectl get events -A --sort-by=.lastTimestamp` для общего взгляда
*   **В:** Как отличить проблему приложения от проблемы кластера?
    *   **О:** Если describe показывает Running, а приложение не работает - проблема в приложении
*   **В:** Что делать если логи не помогают?
    *   **О:** Переходить к exec для непосредственной диагностики внутри контейнера

**7. Типовые примеры/сценарии:**
*   **Сценарий:** Приложение не отвечает на запросы
*   **Действия:**
    1. `kubectl get pods` - проверяем состояние пода
    2. `kubectl describe pod` - смотрим события и условия
    3. `kubectl logs` - анализируем логи приложения
    4. `kubectl exec` - проверяем доступность изнутри
    5. `kubectl port-forward` + curl - тестируем доступность локально
*   **Пояснение:** Последовательный подход экономит время на диагностике
