**1. Визуальный ряд:**
*   Скриншот терминала с выводом команд:
    ```bash
    kubectl describe pod/<pod-name>
    kubectl logs <pod-name> --previous
    kubectl logs <pod-name> -f --tail=50
    ```
*   Сравнительная таблица: `describe` vs `logs` (что показывают, когда использовать)
*   Анатомия вывода `kubectl describe` с выделением ключевых секций:
    *   Events (события)
    *   Conditions (условия)
    *   Containers (состояние контейнеров)
*   Схема работы: Взаимосвязь между событиями (Events) и логированием

**2. Демо-сценарий:**
*   Live-демонстрация диагностики проблемного пода:
    ```bash
    # Смотрим детальную информацию о поде
    kubectl describe pod/<problem-pod>
    
    # Анализируем логи текущего контейнера
    kubectl logs <problem-pod> --tail=100
    
    # Смотрим логи предыдущего контейнера (если был перезапуск)
    kubectl logs <problem-pod> --previous
    
    # Мониторим логи в реальном времени
    kubectl logs <problem-pod> -f --tail=50
    
    # Смотрим логи конкретного контейнера в поде
    kubectl logs <problem-pod> -c <container-name>
    ```

**3. Ключевые тезисы:**
*   "`kubectl describe` — ваш 'рентген' для пода: показывает всю внутреннюю структуру и историю событий"
*   "Секция Events в describe — первое место, куда нужно смотреть при диагностике проблем"
*   "`kubectl logs --previous` — спасение при анализе упавших контейнеров"
*   "Флаг `-f` (follow) для мониторинга логов в реальном времени"
*   "Комбинация describe + logs дает 90% ответов при диагностике проблем"

**4. Описание для выступающего:**
Показать методологию анализа: сначала describe для общего понимания проблемы (события, условия), затем logs для детального анализа работы приложения. Важно научить слушателей читать и интерпретировать события Kubernetes (FailedScheduling, ImagePullBackOff, CrashLoopBackOff).

**5. Связь с прошлыми материалами:**
*   Из чата: "а можно ли как-то выводить дескрайб без службных полей?" -> показать `kubectl neat`
*   Из субтитров: "Глубокая диагностика - kubectl describe" (прямая связь с темой)
*   Из чата: "Если контейнеров несколько, логи какого по дефолту показываются?" -> объяснить выбор контейнера

**6. Типовые вопросы и ответы (Q&A):**
*   **В:** Как фильтровать вывод describe?
    *   **О:** Использовать `grep` или `kubectl neat` для очистки служебных полей
*   **В:** Что делать если логи слишком объемные?
    *   **О:** Использовать `--tail`, `--since` или отправлять логи в централизованную систему
*   **В:** Как читать события (Events)?
    *   **О:** Обращать внимание на тип (Normal/Warning), причину и сообщение

**7. Типовые примеры/сценарии:**
*   **Сценарий:** Под в состоянии CrashLoopBackOff
*   **Действия:**
    1. `kubectl describe pod` - смотрим события и последнее состояние
    2. `kubectl logs --previous` - смотрим логи предыдущего запуска
    3. Анализируем причину падения
*   **Пояснение:** Последовательность действий для диагностики циклических перезапусков
