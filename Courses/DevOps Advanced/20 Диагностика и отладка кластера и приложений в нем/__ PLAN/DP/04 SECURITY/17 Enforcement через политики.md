**1. Визуальный ряд:**
*   Схема работы admission controllers: Запрос -> Validation/Mutation -> Решение
*   Сравнительная таблица инструментов политик:
   
| Инструмент           | Тип политик   | Сложность | Особенности    |
| -------------------- | ------------- | --------- | -------------- |
| **Kyverno**          | Декларативные | Низкая    | Native K8s API |
| **OPA/Gatekeeper**   | Универсальные | Высокая   | Rego язык      |
| **Kubewarden**       | WASM-based    | Средняя   | Безопасность   |
| **PSP (deprecated)** | Встроенные    | -         | Устаревший     |
   
*   Пример политики Kyverno:
    ```yaml
    apiVersion: kyverno.io/v1
    kind: ClusterPolicy
    metadata:
      name: require-labels
    spec:
      validationFailureAction: Enforce
      rules:
      - name: check-labels
        match:
          resources:
            kinds:
            - Pod
        validate:
          message: "All pods must have 'app' and 'env' labels"
          pattern:
            metadata:
              labels:
                app: "?*"
                env: "?*"
    ```
*   Скриншот отклоненного создания пода из-за политики

**2. Демо-сценарий:**
*   Создание и тестирование политик:
    ```bash
    # Установка Kyverno
    kubectl create -f https://github.com/kyverno/kyverno/releases/latest/download/install.yaml
    
    # Применение политики
    kubectl apply -f require-labels-policy.yaml
    
    # Попытка создать под без labels
    kubectl run test --image=nginx
    # Должен получить ошибку валидации
    ```

**3. Ключевые тезисы:**
*   "Политики — это 'правила дорожного движения' для вашего кластера"
*   "Kyverno — самый простой способ начать, использует привычный YAML"
*   "OPA/Gatekeeper — более мощный но сложный, требует изучения Rego"
*   "ValidationFailureAction: Audit vs Enforce — сначала аудит, потом enforcement"
*   "Политики должны быть частью GitOps и code review"

**4. Описание для выступающего:**
Показать как политики автоматически обеспечивают compliance и безопасность. Важно объяснить разницу между audit и enforce режимами. Дать практические рекомендации по внедрению.

**5. Связь с прошлыми материалами:**
*   Естественное развитие темы безопасности из предыдущего слайда
*   Использование статического анализа (checkov) для проверки политик
*   Интеграция с CI/CD пайплайнами

**6. Типовые вопросы и ответы (Q&A):**
*   **В:** С чего начать внедрение политик?
    *   **О:** Сначала audit-режим для сбора статистики, затем enforce для критичных правил
*   **В:** Как избежать блокировки workflow разработчиков?
    *   **О:** Давать понятные сообщения об ошибках и быстрые способы исправления
*   **В:** Что делать с legacy-ресурсами?
    *   **О:** Использовать exclude правила или постепенную миграцию

**7. Типовые примеры/сценарии:**
*   **Политика 1:** Запрет privileged контейнеров
*   **Политика 2:** Требование limits/requests CPU/memory
*   **Политика 3:** Проверка образов из trusted registry
*   **Политика 4:** Требование определенных labels/annotations
