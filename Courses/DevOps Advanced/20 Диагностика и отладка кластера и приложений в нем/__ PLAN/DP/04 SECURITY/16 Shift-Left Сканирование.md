**1. Визуальный ряд:**
*   Схема "Shift-Left": Исходный код -> Сборка -> Образ -> Деплой -> **Раннее обнаружение**
*   Сравнительная таблица инструментов сканирования:
   
| Инструмент   | Тип сканирования | Что проверяет  | Интеграция    |
| ------------ | ---------------- | -------------- | ------------- |
| **Trivy**    | Уязвимости       | CVE, конфиги   | CI, Git hooks |
| **Grype**    | Зависимости      | SBOM, CVE      | CI/CD         |
| **Syft**     | Состав пакетов   | SBOM генерация | -             |
| **Checkov**  | Инфраструктура   | Terraform, K8s | Pre-commit    |
| **GitLeaks** | Секреты          | Токены, ключи  | Pre-push      |
   
*   Пример отчета Trivy с критическими уязвимостями
*   Workflow GitLab CI/GitHub Actions с этапами сканирования

**2. Демо-сценарий:**
*   Сканирование на разных этапах:
    ```bash
    # Локально (pre-commit)
    trivy config . --severity CRITICAL
    gitleaks detect --source . --no-git
    
    # В CI пайплайне
    trivy image --exit-code 1 my-app:latest
    checkov -d kubernetes/ --soft-fail
    ```
*   Показать срыв сборки при обнаружении критических уязвимостей

**3. Ключевые тезисы:**
*   "Лучше найти уязвимость до деплоя чем после инцидента"

*   "SBOM (Software Bill of Materials) — must-have для compliance"

**6. Типовые вопросы и ответы (Q&A):**
*   **В:** Сколько false-positive в сканерах?
    *   **О:** Много, поэтому начинайте с CRITICAL и настраивайте исключения
*   **В:** Как обрабатывать legacy-проекты с тысячами уязвимостей?
    *   **О:** Постепенно: сначала отключить сканирование, затем фиксить по 10-20 в неделю
*   **В:** Нужно ли сканировать зависимости разработки?
    *   **О:** Да, особенно для JavaScript/Python где зависимости dev могут попасть в prod
