### **Слайд 7: Проброс портов - `kubectl port-forward`**

*   **Заголовок:** Проброс портов - `kubectl port-forward`
*   **Ключевые элементы (примерный вид слайда):**
    *   Скриншот терминала: `kubectl port-forward svc/my-service 8080:80`
    *   Скриншот терминала: `kubectl port-forward pod/my-pod 9229:9229`
    *   **Визуальная схема пути трафика:**
        ```
        Ваш Компьютер (localhost:8080)
                |
                | (Локальный сокет)
                v
        kubectl client
                |
                | (HTTPS через KUBECONFIG)
                v
        kube-apiserver (на кластере)
                |
                | (Внутренняя сеть кластера)
                v
        Целевой Pod (порт 80)
        ```
    *   Выделение: ⚠️ Трафик идет через API-сервер.
    *   Выделение: Не использовать для high-load.

---

*   **Описание (для выступающего / Расширенное описание темы):**
    *   **Цель слайда:** Представить команду `kubectl port-forward` как инструмент для создания временного сетевого туннеля между локальной машиной и подом или сервисом в кластере. Подчеркнуть её удобство для отладки и ограничения в производительности.
    *   **Ключевое сообщение:** Команда `kubectl port-forward` позволяет получить доступ к порту сервиса или пода на вашей локальной машине (`localhost`), пробрасывая трафик через `kube-apiserver`. Это чрезвычайно полезно для отладки сервисов, которые не доступны извне (например, с типом `ClusterIP`), или для подключения инструментов отладки. Однако важно помнить, что весь трафик проходит через API-сервер, что делает этот метод непригодным для высоконагруженных сценариев.
    *   **Основные тезисы:**
        *   `kubectl port-forward <тип/имя_объекта> <локальный_порт>:<удаленный_порт>` устанавливает туннель.
        *   Можно пробрасывать порты до `pod`, `service`, `replicaset` или `deployment`.
        *   **⚠️ Ограничение 1 (Производительность):** Трафик маршрутизируется через `kube-apiserver`. Это создает нагрузку на API-сервер и увеличивает задержку. Не используйте для постоянного или высоконагруженного доступа.
        *   **⚠️ Ограничение 2 (Балансировка):** Если указать сервис (или `replicaset`/`deployment`), `kubectl` выберет **один конкретный** бэкенд под и будет пробрасывать трафик только к нему. Никакой балансировки не происходит.
        *   **Актуальность 2025:** Улучшена стабильность. Экспериментальная поддержка UDP появилась в более новых версиях `kubectl` (проверьте документацию вашей версии).
        *   Очень удобна для быстрого доступа к веб-интерфейсам внутренних сервисов (например, мониторинг, логирование) или подключения отладчиков.
    *   *(Из PDF 2019, слайд 4.5)* "С помощью этой команды можно быстро "потыкать палочкой" нужный Pod. Проброс трафика происходит через kube-apiserver, поэтому не надо highload. Можно указать не только под, но и сервис (ReplicaSet или Deployment), но проброс порта все равно произойдет на один конкретный под (под упал == forward упал и никакой балансировки)."
    *   *(Из субтитров 2019)* "Kubectl port forward. Про него, я думаю, уже все знают. Соответственно, про него надо знать две вещи. То есть то, что трафик на самом деле идет через кьюб API-сервер, и поэтому никакого high-load делать не надо, иначе API-серверу будет тяжело и больно. Ну и второй момент, если мы делаем порт-форвард на реплика-сет или диплоймент, то Kubectl просто выбирает какой-то конкретный под и пробрасывает порт до него. Соответственно, если мы сделали порт-форвард до какого-то пода, он упал, значит, соответственно, у нас форвард тоже упал, потому что функция вот этого проксирования трафика, порт-форвардинг, она работает на уровне объекта под в API, а не на уровне диплоймента или еще чего-то такого."

*   **Типовые вопросы и ответы по теме слайда:**
    *   **В:** В чем разница между `kubectl port-forward` и `Ingress` или `LoadBalancer` сервисом?
    *   **О:** `Ingress` и `LoadBalancer` предоставляют постоянные, масштабируемые способы доступа к сервисам извне кластера. `kubectl port-forward` - это временный туннель для локальной машины через API-сервер, не предназначенный для внешнего трафика или высокой нагрузки.
    *   **В:** Почему `kubectl port-forward` не подходит для high-load?
    *   **О:** Потому что весь трафик проходит через `kube-apiserver`. API-сервер предназначен для управления кластером, а не для пересылки большого объема пользовательских данных. Это может привести к его перегрузке и деградации производительности всего кластера.
    *   **В:** Если я пробрасываю порт до сервиса, который имеет несколько реплик, к какому поду пойдет трафик?
    *   **О:** `kubectl` выберет **один конкретный** под, соответствующий селектору сервиса, и будет пробрасывать трафик только к нему. Балансировка между репликами не происходит. Если этот конкретный под упадет, проброс портов также перестанет работать.
    *   **В:** Можно ли пробросить UDP порт?
    *   **О:** **(Актуальность 2025)** Поддержка UDP в `kubectl port-forward` появилась в более новых версиях (например, начиная с Kubernetes 1.27 как бета-функция). Проверьте документацию вашей версии `kubectl`. По умолчанию используется TCP.
    *   **В:** Как остановить `kubectl port-forward`?
    *   **О:** Нажмите `Ctrl+C` в терминале, где запущена команда `port-forward`.

*   **Примеры использования / Типовые сценарии:**
    *   **Отладка веб-приложения:** У вас есть веб-приложение внутри кластера с `ClusterIP` сервисом. Вы можете выполнить `kubectl port-forward svc/my-web-app 8080:80` и открыть `http://localhost:8080` в браузере на своей машине для тестирования.
    *   **Подключение удаленного отладчика:** Ваше приложение (например, Node.js или Java) слушает порт отладчика (например, 9229 для Node.js). Вы можете выполнить `kubectl port-forward pod/my-app-pod-xyz 9229:9229` и подключить локальный отладчик IDE к `localhost:9229`.
    *   **Доступ к внутренним UI:** Получить доступ к UI инструментов мониторинга (Prometheus, Grafana в тестовом режиме) или админке базы данных, запущенной внутри кластера.
    *   *(Из субтитров 2019)* "Например, экзек бин баш. В нашем контейнере мы можем запустить баш и что-нибудь потыкать." (Хотя это про `exec`, но иллюстрирует общий контекст отладки/тестирования "здесь и сейчас").

*   **Пример использования для подключения отладчика (Node.js):**
    1.  Убедитесь, что ваше Node.js приложение запущено внутри пода с опцией `--inspect=0.0.0.0:9229` (или `--inspect-brk` для остановки на первой строке).
        ```yaml
        # Пример контейнера в PodSpec
        spec:
          containers:
          - name: my-nodejs-app
            image: my-nodejs-app:latest
            command: ["node", "--inspect=0.0.0.0:9229", "app.js"]
            ports:
            - containerPort: 9229 # Порт отладчика
            - containerPort: 3000 # Порт приложения
        ```
    2.  Найдите имя пода: `kubectl get pods -l app=my-nodejs-app`
    3.  Выполните проброс порта: `kubectl port-forward pod/my-nodejs-app-pod-xyz 9229:9229`
    4.  В вашей локальной IDE (например, VS Code) настройте конфигурацию отладки для подключения к `localhost:9229`.
    5.  Запустите сессию отладки в IDE. Она подключится к процессу Node.js внутри контейнера.

*   **Пример вывода `kubectl port-forward`:**
    ```bash
    $ kubectl port-forward svc/my-internal-service 8080:80
    Forwarding from 127.0.0.1:8080 -> 80
    Forwarding from [::1]:8080 -> 80
    Handling connection for 8080 # <-- Появляется при каждом подключении клиента
    Handling connection for 8080
    ```
    *   **Объяснение:** Команда начинает проброс порта. Она показывает, с каких адресов (`127.0.0.1`, `[::1]` - IPv6 localhost) и портов (`8080`) локально будет доступен сервис. Сообщения `Handling connection` появляются, когда клиент (например, браузер) подключается к `localhost:8080`.
