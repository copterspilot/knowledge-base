### **Слайд 11: Отладка контейнеров - `kubectl debug`**

*   **Часть 1. Ops. Продвинутый `kubectl` и инструменты диагностики**
*   **Заголовок:** Отладка контейнеров - `kubectl debug`
*   **Ключевые элементы (примерный вид слайда):**
    *   Скриншот терминала: `kubectl debug my-pod -it --image=busybox --target=main-container -- sh`
    *   Скриншот терминала: `kubectl debug my-pod --image=nicolaka/netshoot --share-processes --copy-to=my-pod-debug`
    *   Иконка отладки/бага.
    *   Выделение: **Ephemeral Containers** (Временные контейнеры).

---

*   **Описание (для выступающего / Расширенное описание темы):**
    *   **Цель слайда:** Представить команду (или плагин) `kubectl debug` как мощный инструмент для отладки подов, в которых отсутствуют стандартные инструменты диагностики. Подчеркнуть его реализацию через Ephemeral Containers и важность в 2025 году.
    *   **Ключевое сообщение:** Команда `kubectl debug` позволяет создать специальный временный (ephemeral) контейнер внутри уже запущенного пода. Это особенно полезно для отладки подов, созданных из минималистичных образов (например, `scratch`, `distroless`), где отсутствуют оболочки (`sh`, `bash`) или сетевые утилиты (`ping`, `nslookup`). Это современная и рекомендуемая альтернатива ограничениям `kubectl exec`.
    *   **Основные тезисы:**
        *   **Что такое `kubectl debug`:** Это команда (в новых версиях `kubectl`) или отдельный плагин, который реализует функционал **Ephemeral Containers** *(Из субтитров 2019)*.
        *   **Ephemeral Containers:** Это временные контейнеры, которые можно добавить в существующий `Pod` для целей отладки. Они не перезапускаются и завершаются вместе с `Pod` или при завершении их процесса *(Из субтитров 2019)*. **Актуальность 2025:** Ephemeral Containers стали **стабильной функцией** в Kubernetes (с версии 1.25+).
        *   **Преимущества над `exec`:** Позволяет использовать полнофункциональный образ отладки (например, `busybox`, `nicolaka/netshoot`) даже если основной контейнер минималистичный. Можно запускать различные утилиты (например, `tcpdump`, `strace`).
        *   **Режимы работы:**
            *   **Добавление ephemeral container:** `kubectl debug <pod-name> -it --image=<debug-image> --target=<existing-container> -- <command>` *(Из описания слайда 11 в предыдущем диалоге)*.
            *   **Создание копии пода:** `kubectl debug <pod-name> --image=<debug-image> --copy-to=<new-pod-name>`. Создает копию пода с добавленным контейнером отладки. Полезно, если оригинальный под в плохом состоянии *(Из описания слайда 11 в предыдущем диалоге)*.
        *   **Поддержка CRI:** Работает с Docker, containerd, CRI-O *(Из описания слайда 11 в предыдущем диалоге)*.
        *   **Актуальность 2025:** Расширенные возможности, интеграция с IDE *(Из описания слайда 11 в предыдущем диалоге)*.
    *   *(Из PDF 2019, слайд 4.9)* "Это отдельный плагин, позволяет запустить специальный контейнер внутри Pod для отладки и диагностики. Работает в двух режимах- agentless и в режиме с агентом".

*   **Типовые вопросы и ответы по теме слайда:**
    *   **В:** В чем разница между `kubectl exec` и `kubectl debug`?
    *   **О:** `kubectl exec` запускает команду в **уже существующем** контейнере пода. Если в этом контейнере нет нужных инструментов (например, `sh`, `ping`), `exec` не поможет. `kubectl debug` создает **новый временный контейнер** с выбранным вами образом (например, `busybox`), который имеет доступ к тому же `namespace` (сети, файловой системе, процессам), что и другие контейнеры в поде. Это позволяет использовать любые инструменты из образа отладки.
    *   **В:** Что такое Ephemeral Containers?
    *   **О:** Это специальный тип контейнеров в Kubernetes, предназначенный исключительно для отладки. Их можно добавить в существующий `Pod`, они не перезапускаются и не влияют на жизненный цикл основных контейнеров. Они стали стабильной функцией в K8s 1.25+.
    *   **В:** Почему `kubectl debug` лучше, чем `kubectl exec` с минималистичными образами?
    *   **О:** Минималистичные образы (например, `FROM scratch` или `distroless`) не содержат оболочек (`sh`, `bash`) или утилит. `kubectl exec` не может запустить оболочку в таком контейнере. `kubectl debug` обходит это, создавая новый контейнер с полнофункциональным образом отладки.
    *   **В:** Нужно ли устанавливать плагин `kubectl debug`?
    *   **О:** В новых версиях `kubectl` (начиная примерно с 1.23+) команда `kubectl debug` встроена. Ранее требовалась установка отдельного плагина.
    *   **В:** Что такое режимы `agentless` и `с агентом` (из PDF 2019)?
    *   **О:** Это относилось к старому отдельному плагину `kubectl-debug`. `agentless` создавал временный под для каждого дебага. `С агентом` требовал предварительного запуска `DaemonSet` на нодах для ускорения процесса. Во встроенной команде `kubectl debug` эти режимы не используются напрямую, но концепция временного контейнера остается.

*   **Примеры использования / Типовые сценарии:**
    *   **Отладка пода с образом `scratch`:** Основной контейнер собран `FROM scratch`. Выполняете `kubectl debug my-app-pod -it --image=busybox --target=my-app-container -- sh` для получения оболочки.
    *   **Анализ сетевых проблем:** Под не может достичь внешнего сервиса. Выполняете `kubectl debug my-app-pod --image=nicolaka/netshoot --target=my-app-container -- nslookup external-service.com` или `kubectl debug ... -- tcpdump -i any -w /tmp/dump.pcap` для захвата трафика.
    *   **Проверка файловой системы:** Использование `kubectl debug ... -- ls /app/config/` или `kubectl debug ... -- cat /etc/resolv.conf`.
    *   *(Из PDF 2019, слайд 5.3)* "pulling image nicolaka/netshoot:latest... starting debug container... bash-5.0# ps aux" *(Демонстрирует запуск отладочного контейнера с `netshoot`)*.
    *   *(Из PDF 2019, слайд 5.4)* "bash-5.0# cat/proc/1/root/email_server/email_server.py" *(Демонстрирует доступ к файлам основного процесса через `/proc`)*.
    *   *(Из PDF 2019, слайд 5.5)* "bash-5.0# strace-p 7-c" *(Демонстрирует трассировку системных вызовов)*.

*   **Пример вывода `kubectl debug`:**
```bash
    # Добавление ephemeral container и запуск оболочки
    $ kubectl debug my-app-pod-7d5b8c9c4-xl2v9 -it --image=busybox --target=my-app-container -- sh
    Creating debugging pod node with command: sh
    If you don't see a command prompt, try pressing enter.
    / # ls /
    bin   dev   etc   home  proc  root  sys   tmp   usr   var
    / # ps aux | grep my-app
    1 root 0:05 /my-app-binary --config /app/config.yaml
    123 root 0:00 grep my-app
    / # exit
```

> **Объяснение:** Создается временный контейнер с образом `busybox`. Команда `sh` запускается внутри этого контейнера. Из этой оболочки можно исследовать окружение пода (файлы, процессы) и запускать утилиты, доступные в `busybox`.
