### **Слайд 8: Логи - `kubectl logs`**

*   **Заголовок:** Логи - `kubectl logs`
*   **Ключевые элементы (примерный вид слайда):**
    *   Скриншот терминала: `kubectl logs my-pod`
    *   Скриншот терминала: `kubectl logs my-pod --previous`
    *   Скриншот терминала: `kubectl logs -l app=my-app --tail=10 --follow`
    *   Иконка консоли/логов.

---

*   **Описание (для выступающего / Расширенное описание темы):**
    *   **Цель слайда:** Представить команду `kubectl logs` как основной инструмент для просмотра стандартного вывода (stdout/stderr) контейнеров в подах. Подчеркнуть её важность для понимания поведения приложений и диагностики ошибок.
    *   **Ключевое сообщение:** Команда `kubectl logs` предоставляет доступ к потоку сообщений, которые приложение выводит в стандартные потоки вывода и ошибок внутри контейнера. Это самый прямой способ понять, *что именно* делает приложение, какие ошибки оно генерирует и каков его внутренний статус, что критично важно при отладке сбоев или странного поведения.
    *   **Основные тезисы:**
        *   `kubectl logs <pod-name>` - показывает логи основного контейнера пода.
        *   **Множество контейнеров:** Если в поде несколько контейнеров, необходимо указать конкретный контейнер: `kubectl logs <pod-name> -c <container-name>`. *(Из чата 2019)*
        *   **Полезные флаги:**
            *   `--follow` или `-f`: Следить за новыми сообщениями в реальном времени (аналог `tail -f`).
            *   `--tail <число>`: Показать последние N строк лога.
            *   `--since <длительность>` / `--since-time <время>`: Показать логи за последние X минут/секунд или с определенного момента времени. *(Из субтитров 2019)*
            *   `--previous` или `-p`: Показать логи из *предыдущего* экземпляра контейнера (очень полезно, если контейнер крашнулся и перезапустился). *(Из субтитров 2019)*
            *   `--all-containers=true`: Показать логи из всех контейнеров пода в одном потоке.
            *   `--selector <label-selector>`: Показать логи из всех подов, соответствующих метке. *(Из субтитров 2019)*
        *   **Актуальность 2025:** Улучшена поддержка JSON-логов, фильтрация по времени (`--since`, `--until`), поддержка `--previous` для init-контейнеров.
        *   `logs` работает с основным приложением в контейнере. Для более глубокой интроспекции файловой системы или процессов используются `exec`, `debug`, `inspektor-gadget`.
    *   *(Из PDF 2019, слайд 4.6)* "Показывает логи контейнеров в поде. Удобно делать так: --since или --since-time, --selector, --previous".
    *   *(Из субтитров 2019)* "Kubectl logs, соответственно, это тоже должно быть в копилочке каждого администратора. Она показывает логи из пода, в частности, конкретного контейнера, основного контейнера пода... Но если мы укажем all containers true, она покажет логи нам из всех контейнеров... *   **Типовые вопросы и ответы по теме слайда:**
    *   **В:** Что делать, если `kubectl logs` не показывает никаких логов?
    *   **О:** Приложение может не писать в stdout/stderr, или логи могут быть перенаправлены в файл внутри контейнера. Также проверьте, правильно ли указано имя пода/контейнера. Если контейнер недавно крашнулся, используйте `--previous`.
    *   **В:** Почему приложение может не писать логи в stdout/stderr?
    *   **О:** Это ошибка в приложении или его конфигурации. Многие фреймворки и языки по умолчанию выводят логи в stdout/stderr, но приложение может быть настроено на запись в файл или использовать специфичные для себя механизмы логирования. В контексте Kubernetes стандартная практика - писать логи в потоки вывода.
    *   **В:** Как посмотреть логи init-контейнера?
    *   **О:** Используйте `kubectl logs <pod-name> -c <init-container-name>`. В новых версиях `kubectl` (и в 2025 году) также может поддерживаться `--previous` для init-контейнеров, если они уже завершились.
    *   **В:** Чем `kubectl logs --follow` отличается от `kubectl exec -it <pod> -- tail -f /var/log/app.log`?
    *   **О:** `kubectl logs --follow` читает стандартные потоки вывода контейнера, управляемые Kubernetes и CRI. `kubectl exec ... tail -f ...` выполняет команду *внутри* работающего контейнера для чтения файла. Первый способ стандартен и надежен для логов приложения, второй - для случаев, когда приложение пишет в файл и этот файл доступен внутри контейнера.
    *   **В:** Можно ли фильтровать логи, полученные через `kubectl logs`?
    *   **О:** `kubectl logs` сама по себе не предоставляет мощных фильтров по содержимому. Обычно для фильтрации используются стандартные Unix-утилиты, например, `kubectl logs <pod> | grep "ERROR"` или `kubectl logs <pod> | jq '.'` (для JSON-логов).

*   **Примеры использования / Типовые сценарии:**
    *   **Диагностика `CrashLoopBackOff`:** `kubectl logs <pod-name> --previous` - просмотр логов контейнера, который крашнулся.
    *   **Мониторинг в реальном времени:** `kubectl logs -f <pod-name>` - следить за логами работающего приложения.
    *   **Поиск ошибок:** `kubectl logs <pod-name> | grep -i "exception\|error"` - поиск строк с ошибками.
    *   **Просмотр последних событий:** `kubectl logs --tail=50 <pod-name>` - показать последние 50 строк.
    *   **Анализ логов нескольких подов:** `kubectl logs -l app=my-web-app --tail=10` - показать последние 10 строк логов из всех подов с меткой `app=my-web-app`.
    *   *(Из PDF 2019, слайд 4.6)* "# Показать последние 10 строк лога всех контейнеров пода и затем выводить новые сообщения `kubectl logs --all-containers=true --follow --tail=10`"

*   **Пример вывода `kubectl logs`:**
    ```bash
    $ kubectl logs my-app-pod-7d5b8c9c4-xl2v9
    2025-01-03T15:00:00.000Z INFO  [main] Starting application...
    2025-01-03T15:00:01.234Z INFO  [main] Connecting to database at db-service:5432
    2025-01-03T15:00:02.567Z ERROR [main] Failed to connect to database: Connection timed out
    2025-01-03T15:00:02.568Z INFO  [main] Retrying in 5 seconds...
    ```
    *   **Объяснение:** Этот вывод показывает типичные сообщения лога приложения: информационные сообщения о запуске и ошибках подключения к базе данных.
