### **Слайд 4: Анализ ресурсов - `kubectl top`**

*   **Заголовок:** Анализ ресурсов - `kubectl top`
*   **Ключевые элементы (примерный вид слайда):**
    *   Скриншот терминала: `kubectl top nodes`
    *   Скриншот терминала: `kubectl top pods -n <namespace>`
    *   Скриншот терминала: `kubectl top pods --sort-by=memory`
    *   Иконка Metrics Server / Prometheus
    *   Текст: "Требует `metrics-server` или адаптера (Prometheus Adapter)"

---

*   **Описание (для выступающего / Расширенное описание темы):**
    *   **Цель слайда:** Познакомить с командой `kubectl top` как основным инструментом для мониторинга потребления ресурсов (CPU, память) подами и нодами. Подчеркнуть её важность для диагностики проблем производительности и планирования ресурсов.
    *   **Ключевое сообщение:** Команда `kubectl top` предоставляет быстрый и удобный способ увидеть, какие поды или ноды потребляют больше всего ресурсов. Это критически важно для диагностики проблем, таких как утечки памяти, избыточное потребление CPU или выселение подов (Eviction). Однако для работы этой команды в кластере должен быть установлен и запущен `metrics-server` (или совместимый адаптер, например, Prometheus Adapter).
    *   **Основные тезисы:**
        *   `kubectl top node` показывает общее потребление ресурсов каждой ноды кластера (CPU, память, процент использования).
        *   `kubectl top pod` показывает потребление ресурсов каждым подом (по умолчанию в текущем namespace). Можно указать конкретный namespace (`-n <ns>`) или все namespaces (`-A`).
        *   Поддерживает фильтрацию по меткам (`--selector`) и сортировку (`--sort-by=cpu|memory`).
        *   **Актуальность 2025:** Поддержка метрик `ephemeral-storage` и более продвинутые опции сортировки.
        *   **Зависимость:** Требуется `metrics-server` (или аналог) в кластере. В большинстве облачных и современных локальных дистрибутивов он устанавливается по умолчанию или легко добавляется.
        *   **Будущее/Альфа-функции:** Команда `kubectl alpha top` может появляться в новых версиях `kubectl` для тестирования экспериментальных функций мониторинга. Например, в K8s 1.29+ появилась альфа-поддержка `kubectl alpha events`, показывающая события кластера. Аналогично, `kubectl alpha top` может предлагать расширенные или альтернативные представления метрик, например, с разбивкой по контейнерам по умолчанию или поддержкой других типов ресурсов. Следите за обновлениями `kubectl` и SIG CLI для новых возможностей.
    *   *(Из PDF 2019, слайд 4.1)* "Выводит список нод или подов и потребляемых ресурсов. --selector- задать фильтр по меткам --sort-by- отсортировать по cpu\|memory".
    *   *(Из субтитров 2019)* "Самая простая — это команда kubectl top, которая позволяет делать top-node и top-pod и отсортировать по потреблению ресурсов, по потреблению процессорной мощности наши поды или наши ноды. Соответственно, у кого сколько core занято, сколько там утилизации процессора у кого, сколько там утилизировано памяти и так далее, ну и процентов посмотреть. ... Единственный минус этой штуки, это то, что она требует наличия метрик-сервера или хипстера по кластере."
    *   *(Из чата 2019)* Вопрос о том, как вывести `top` для конкретных контейнеров (неявно подразумевается `--containers` или `--all-containers` в новых версиях или необходимости смотреть в `describe`).

*   **Типовые вопросы и ответы по теме слайда:**
    *   **В:** Что делать, если `kubectl top` не работает или выдает ошибку "Metrics API not available"?
    *   **О:** Это означает, что в кластере не установлен `metrics-server` или он не работает. Необходимо установить его (например, через Helm: `helm install metrics-server metrics-server/metrics-server` или вручную через манифесты). Для некоторых облачных провайдеров могут использоваться их собственные решения (например, GKE может использовать GMP - Google Metric Provider).
    *   **В:** Почему `kubectl top pod` показывает только один контейнер, если в поде их несколько?
    *   **О:** По умолчанию `kubectl top pod` показывает метрики для основного контейнера. Чтобы увидеть метрики для всех контейнеров пода, используйте флаг `--containers` (например, `kubectl top pod <pod-name> --containers`). В более новых версиях `kubectl` также может поддерживаться `--all-containers`.
    *   **В:** Можно ли сортировать вывод `kubectl top pods` по использованию памяти?
    *   **О:** Да, используйте флаг `--sort-by`. Например: `kubectl top pods --sort-by=memory`.
    *   **В:** Показывает ли `kubectl top` использование ephemeral-storage?
    *   **О:** **(Актуальность 2025)** Да, современные версии `metrics-server` и `kubectl` поддерживают отображение метрик `ephemeral-storage`. Проверьте документацию вашего `metrics-server`.
    *   **В:** Чем `kubectl top` отличается от полноценного мониторинга типа Prometheus + Grafana?
    *   **О:** `kubectl top` предоставляет базовую информацию о текущем потреблении ресурсов. Prometheus/Grafana позволяют собирать, хранить, анализировать исторические данные, создавать сложные дашборды и алерты. `kubectl top` - это инструмент для быстрой диагностики "здесь и сейчас", а Prometheus - для комплексного мониторинга.
    *   **В:** Что такое `kubectl alpha top`?
    *   **О:** `kubectl alpha` используется для доступа к экспериментальным функциям, которые находятся на стадии Alpha. `kubectl alpha top` может содержать новые или измененные функции мониторинга ресурсов, которые еще не вошли в стабильную версию `kubectl top`. Использование альфа-функций может быть нестабильным. Проверяйте документацию вашей версии `kubectl` (`kubectl alpha --help`) для получения актуальной информации.

*   **Примеры использования / Типовые сценарии:**
    *   **Диагностика высокой нагрузки:** `kubectl top nodes` - чтобы понять, какие ноды перегружены.
    *   **Поиск проблемного пода:** `kubectl top pods --sort-by=cpu -n my-app-namespace` - чтобы найти под, потребляющий больше всего CPU.
    *   **Расследование OOMKilled:** `kubectl top pods --sort-by=memory` - чтобы увидеть, какие поды используют больше всего памяти.
    *   **Планирование ресурсов:** Анализ `kubectl top` помогает определить, правильно ли установлены `requests` и `limits` для контейнеров.
    *   *(Из субтитров 2019)* "показать, как выглядят ивенты в кластере... можно посмотреть все ивенты по всем наимспейсам... видно, что происходит какое-то убийство контейнеров... можно, соответственно, понаблюдать... можно сделать команду watch only, которая просто покажет последние события". (Хотя это про `get events`, но показывает общий контекст мониторинга состояния).
    *   **Пример вывода `kubectl top pods --containers`:**
        ```bash
        $ kubectl top pods --containers -n my-application
        NAME                         CPU(cores)   MEMORY(bytes)   CONTAINER
        web-app-7d5b8c9c4-xl2v9      15m          45Mi            web-app
        web-app-7d5b8c9c4-xl2v9      1m           25Mi            istio-proxy
        web-app-7d5b8c9c4-rz5p2      18m          48Mi            web-app
        web-app-7d5b8c9c4-rz5p2      2m           26Mi            istio-proxy
        cache-redis-6b7d5f9c4-abc12  5m           120Mi           redis
        database-5c9b8f7d5c-def34    42m          310Mi           postgres
        database-5c9b8f7d5c-def34    8m           65Mi            metrics-exporter
        ```
        *   **Объяснение:** Этот вывод показывает использование CPU и памяти для каждого контейнера внутри каждого пода. Это особенно полезно для подов с sidecar-контейнерами (например, `istio-proxy`).

Вот короткий пример вывода команды `kubectl top node`:

```bash
$ kubectl top node
NAME                        CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
gke-cluster-1-pool-1-abc123  150m         15%    1200Mi          30%
gke-cluster-1-pool-1-def456  80m          8%     800Mi           20%
gke-cluster-1-pool-2-ghi789  300m         30%    2500Mi          62%
```

**Объяснение:**
*   **NAME**: Имя ноды в кластере.
*   **CPU(cores)**: Текущее использование CPU в миллиядрах (150m = 0.15 ядер CPU).
*   **CPU%**: Процент использования выделенного CPU.
*   **MEMORY(bytes)**: Текущее использование памяти.
*   **MEMORY%**: Процент использования выделенной памяти.
