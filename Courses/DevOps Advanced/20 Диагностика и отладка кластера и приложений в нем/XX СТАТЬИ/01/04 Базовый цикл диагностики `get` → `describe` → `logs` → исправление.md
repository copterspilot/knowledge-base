### **Статья 4: Базовый цикл диагностики: `get` → `describe` → `logs` → исправление**

#### **Введение**

Когда вы слышите, что сервис упал, не паникуйте. У вас есть систематический процесс — **базовый цикл диагностики**. Этот цикл из четырех простых шагов поможет вам найти причину проблемы в 90% случаев. Он основан на лучших практиках, описанных в `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices`, и является фундаментом для любого инженера DevOps.

#### **Шаг 1: `kubectl get` — Получение общей картины**

Цель этого шага — быстро оценить общее состояние кластера и найти "больные" ресурсы.

*   **Что делать:** Используйте команду `kubectl get` для просмотра списка ресурсов.
*   **На что смотреть:** Обратите внимание на столбец **STATUS**. Ищите подозрительные статусы:
    *   `CrashLoopBackOff`: Под постоянно перезапускается.
    *   `ImagePullBackOff`: Не удается скачать образ.
    *   `Error`: Общая ошибка при запуске.
*   **Пример:**
    ```bash
    # Показать все поды во всех namespace'ах
    kubectl get pods -A
    ```
    Эта команда покажет вам, где именно возникла проблема. Предположим, вы нашли под `my-app-pod-7d5b8c9c4-xl2v9` в статусе `CrashLoopBackOff`. Это ваш первый "подозреваемый".

#### **Шаг 2: `kubectl describe` — Глубокая диагностика**

Теперь, когда вы знаете, какой под в проблеме, нужно заглянуть внутрь, чтобы понять "почему".

*   **Что делать:** Используйте команду `kubectl describe` для получения детальной информации о поде.
*   **На что смотреть:** Самая ценная информация находится в секции **Events** в самом низу вывода. Здесь Kubernetes записывает все ключевые события в жизни пода.
*   **Пример:**
    ```bash
    kubectl describe pod my-app-pod-7d5b8c9c4-xl2v9
    ```
    В секции `Events` вы можете увидеть сообщение: `Failed to pull image "my-registry.com/my-app:v1.2": rpc error: code = Unknown desc = Error response from daemon: Get https://my-registry.com/v2/: net/http: request canceled while waiting for connection`. Это четкий указатель на проблему с доступом к реестру образов.

#### **Шаг 3: `kubectl logs` — Анализ вывода приложения**

Если `describe` не дал окончательного ответа, или вы хотите увидеть ошибки из самого приложения, переходите к логам.

*   **Что делать:** Используйте команду `kubectl logs` для просмотра вывода контейнера.
*   **На что смотреть:** Ищите стектрейсы (stack traces), сообщения об ошибках (errors), исключения (exceptions).
*   **Ключевой флаг:** `--previous`. Он позволяет посмотреть логи **упавшего** контейнера. Без него вы увидите только логи текущего (возможно, еще не запущенного) контейнера.
*   **Пример:**
    ```bash
    # Показать последние 20 строк логов упавшего контейнера
    kubectl logs my-app-pod-7d5b8c9c4-xl2v9 --previous --tail=20
    ```
    Вы можете увидеть ошибку: `ConnectionRefusedError: [Errno 111] Connection refused`. Это говорит о том, что приложение не может подключиться к зависимому сервису (например, базе данных).

#### **Шаг 4: Исправление**

Теперь, когда вы знаете причину, можно приступить к исправлению. Это может быть:
*   Исправление имени образа в манифесте.
*   Настройка прав доступа к приватному реестру.
*   Проверка конфигурации зависимого сервиса.

#### **Заключение**

Следуя этому простому циклу, вы превратите хаотичный процесс поиска ошибок в систематическую диагностику. Этот подход работает для большинства распространенных проблем. В следующей статье мы рассмотрим, как ускорить этот процесс с помощью продвинутых инструментов, таких как `stern` и `k9s`.
