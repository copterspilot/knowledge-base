### **Статья 3: `kubectl` — фундамент: `get`, `describe`, `logs`, `top`**

#### **Введение**

`kubectl` — это ваш единственный инструмент для взаимодействия с кластером Kubernetes. Он является вашим "проводником" в мире контейнеров. Все, что вы делаете — от развертывания приложений до диагностики проблем — проходит через `kubectl`. В этой статье мы рассмотрим четыре основные команды, которые составляют фундамент для диагностики. Как указано в `Burns B., Villalba E., Strebel D., Evenson L. - Kubernetes Best Practices`, освоение этих команд — первый шаг на пути к мастерству DevOps.

#### **`kubectl get` — Получение информации**

Команда `get` — это ваша первая и самая важная команда. Она позволяет получить список ресурсов и их текущее состояние.

*   **Что делает:** Показывает список ресурсов (pods, nodes, services, deployments и т.д.).
*   **На что смотреть:** Статус ресурсов. Ищите `Running`, `CrashLoopBackOff`, `ImagePullBackOff`.
*   **Примеры:**
    ```bash
    # Показать все поды во всех namespace'ах
    kubectl get pods -A
    
    # Показать поды с меткой app=frontend
    kubectl get pods -l app=frontend
    
    # Наблюдать за изменениями в реальном времени
    kubectl get pods -w
    ```
    Команда `get` — это ваш "радар". Она позволяет быстро понять, где именно возникла проблема.

#### **`kubectl describe` — Глубокая диагностика**

Когда вы нашли под в проблеме, пора заглянуть внутрь. Команда `describe` предоставляет детальную информацию о ресурсе.

*   **Что делает:** Показывает подробную информацию о конкретном ресурсе, включая его конфигурацию, состояние и **события (Events)**.
*   **На что смотреть:** Секцию `Events` в самом низу вывода. Здесь Kubernetes записывает все ключевые события в жизни пода.
*   **Пример:**
    ```bash
    kubectl describe pod my-app-pod-7d5b8c9c4-xl2v9
    ```
    Если под не может запуститься, в `Events` вы можете увидеть сообщение `Failed to pull image` или `Insufficient cpu`. Это и есть корень проблемы.

#### **`kubectl logs` — Анализ логов приложения**

Команда `logs` позволяет вам увидеть, что пишет само приложение. Это критически важно для диагностики ошибок в коде.

*   **Что делает:** Показывает логи, выводимые процессом в контейнере.
*   **На что смотреть:** Ошибки (errors), исключения (exceptions), стектрейсы (stack traces).
*   **Примеры:**
    ```bash
    # Показать последние 20 строк логов
    kubectl logs my-app-pod-7d5b8c9c4-xl2v9 --tail=20
    
    # Показать логи в реальном времени (follow)
    kubectl logs my-app-pod-7d5b8c9c4-xl2v9 -f
    
    # КРИТИЧЕСКИ ВАЖНО: Показать логи УПАВШЕГО контейнера
    kubectl logs my-app-pod-7d5b8c9c4-xl2v9 --previous
    ```
    Флаг `--previous` — ваш лучший друг при `CrashLoopBackOff`. Без него вы увидите только логи текущего (возможно, еще не упавшего) контейнера.

#### **`kubectl top` — Анализ потребления ресурсов**

Иногда проблема не в коде, а в ресурсах. Команда `top` помогает понять, голодает ли ваш под в CPU или памяти.

*   **Что делает:** Показывает текущее потребление CPU и памяти подами и узлами.
*   **На что смотреть:** Сравнение потребления с выделенными `requests` и `limits`.
*   **Примеры:**
    ```bash
    # Показать потребление ресурсов узлами
    kubectl top nodes
    
    # Показать потребление ресурсов подами, отсортированными по памяти
    kubectl top pods --sort-by=memory
    ```
    **Важно:** Для работы `kubectl top` требуется `metrics-server`. Если команда не работает, проверьте, установлен ли он в кластере.

#### **Заключение**

Эти четыре команды — ваш фундамент. Они являются основой для всего, что вы будете делать в Kubernetes. В следующей статье мы покажем, как использовать эти команды в систематическом цикле диагностики: `get` → `describe` → `logs` → исправление.
