### **Статья 32: Чек-лист: 5 шагов диагностики упавшего Pod'а**

#### **Введение**

Когда под падает, не паникуйте. Достаньте этот чек-лист и следуйте по пунктам. Сначала используйте `get`, чтобы найти проблемный под. Затем `describe`, чтобы посмотреть события — это часто дает прямой ответ. Далее `logs --previous`, чтобы увидеть, что упало в последний раз. Если нужно, зайдите внутрь с помощью `exec` или `debug`. И, наконец, проверьте, не голодает ли он в ресурсах. Как указано в `Muschko Benjamin - Certified Kubernetes Application Developer (CKAD) Study Guide`, это базовый цикл, который должен быть отработан до автоматизма.

#### **Шаг 1: `kubectl get pods` — Поиск проблемного пода**

Цель этого шага — быстро оценить общее состояние кластера и найти "больной" ресурс.

*   **Что делать:** Используйте команду `kubectl get pods` для просмотра списка подов.
*   **На что смотреть:** Статус пода. Ищите подозрительные статусы:
    *   `CrashLoopBackOff`: Под постоянно перезапускается.
    *   `ImagePullBackOff`: Не удается скачать образ.
    *   `Error`: Общая ошибка при запуске.
*   **Пример:**
    ```bash
    # Показать все поды во всех namespace'ах
    kubectl get pods -A
    ```
    Эта команда покажет вам, где именно возникла проблема. Предположим, вы нашли под `my-app-pod-7d5b8c9c4-xl2v9` в статусе `CrashLoopBackOff`. Это ваш первый "подозреваемый".

#### **Шаг 2: `kubectl describe pod <имя>` — Анализ событий (Events)**

Теперь, когда вы знаете, какой под в проблеме, нужно заглянуть внутрь, чтобы понять "почему".

*   **Что делать:** Используйте команду `kubectl describe pod` для получения детальной информации о поде.
*   **На что смотреть:** Самая ценная информация находится в секции **Events** в самом низу вывода. Здесь Kubernetes записывает все ключевые события в жизни пода.
*   **Пример:**
    ```bash
    kubectl describe pod my-app-pod-7d5b8c9c4-xl2v9
    ```
    В секции `Events` вы можете увидеть сообщение: `Failed to pull image "my-registry.com/my-app:v1.2": rpc error: code = Unknown desc = Error response from daemon: Get https://my-registry.com/v2/: net/http: request canceled while waiting for connection`. Это четкий указатель на проблему с доступом к реестру образов.

#### **Шаг 3: `kubectl logs <имя> --previous` — Анализ логов приложения**

Если `describe` не дал окончательного ответа, или вы хотите увидеть ошибки из самого приложения, переходите к логам.

*   **Что делать:** Используйте команду `kubectl logs` для просмотра вывода контейнера.
*   **На что смотреть:** Ищите стектрейсы (stack traces), сообщения об ошибках (errors), исключения (exceptions).
*   **Ключевой флаг:** `--previous`. Он позволяет посмотреть логи **упавшего** контейнера. Без него вы увидите только логи текущего (возможно, еще не запущенного) контейнера.
*   **Пример:**
    ```bash
    # Показать последние 20 строк логов упавшего контейнера
    kubectl logs my-app-pod-7d5b8c9c4-xl2v9 --previous --tail=20
    ```
    Вы можете увидеть ошибку: `ConnectionRefusedError: [Errno 111] Connection refused`. Это говорит о том, что приложение не может подключиться к зависимому сервису (например, базе данных).

#### **Шаг 4: `kubectl exec -it <имя> -- /bin/sh` — Интерактивная диагностика**

Если предыдущие шаги не дали полной картины, попробуйте войти внутрь контейнера.

*   **Что делать:** Используйте команду `kubectl exec` для запуска интерактивной оболочки.
*   **На что смотреть:** Проверьте переменные окружения (`env`), файловую систему (`ls`, `cat`), попробуйте подключиться к зависимостям (`curl`, `nslookup`).
*   **Пример:**
    ```bash
    # Запустить интерактивную оболочку в контейнере
    kubectl exec -it my-app-pod-7d5b8c9c4-xl2v9 -- /bin/sh
    ```
*   **Альтернатива для `distroless` образов:** Если в контейнере нет `/bin/sh`, используйте `kubectl debug` для создания ephemeral-контейнера.

#### **Шаг 5: `kubectl top pod <имя>` — Проверка потребления ресурсов**

Иногда проблема не в коде, а в ресурсах. Команда `top` помогает понять, голодает ли ваш под в CPU или памяти.

*   **Что делать:** Показывает текущее потребление CPU и памяти подами и узлами.
*   **На что смотреть:** Сравнение потребления с выделенными `requests` и `limits`.
*   **Пример:**
    ```bash
    kubectl top pod my-app-pod-7d5b8c9c4-xl2v9
    ```
    **Важно:** Для работы `kubectl top` требуется `metrics-server`. Если команда не работает, проверьте, установлен ли он в кластере.
