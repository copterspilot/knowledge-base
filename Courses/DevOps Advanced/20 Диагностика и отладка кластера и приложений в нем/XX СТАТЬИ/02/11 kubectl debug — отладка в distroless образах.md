### **Статья 11: `kubectl debug` — отладка в `distroless` образах**

#### **Введение**

Представьте, что ваше приложение падает, и вы пытаетесь войти в контейнер с помощью `kubectl exec`. Вы получаете ошибку 'executable file not found'. Почему? Потому что образ `distroless` не содержит `sh` или `bash`. Это хорошо для безопасности, но плохо для отладки. Решение — `kubectl debug`. Эта команда создает временный контейнер *внутри того же пода*, который имеет доступ к его процессам, сети и файловой системе. Как указано в `Muschko Benjamin - Certified Kubernetes Application Developer (CKAD) Study Guide`, умение работать с `kubectl debug` — это ключевой навык для CKA и CKAD.

#### **Проблема: Безоболочечные образы**

`distroless` образы — это стандарт де-факто для безопасных приложений. Они содержат только ваше приложение и его зависимости, исключая все ненужные утилиты (включая `sh`, `bash`, `ls`, `ps` и т.д.). Это значительно уменьшает поверхность атаки, но делает традиционные методы отладки (`exec`) невозможными.

#### **Решение: Ephemeral Containers и `kubectl debug`**

Kubernetes предоставляет решение в виде **Ephemeral Containers** — специального типа контейнера, предназначенного исключительно для отладки. Команда `kubectl debug` — это удобный CLI-интерфейс для их создания.

*   **Что делает:** `kubectl debug` создает временный контейнер внутри целевого пода и подключает к нему ваш терминал.
*   **Как это работает:**
    1.  Вы запускаете команду `kubectl debug`, указывая имя пода и образ с отладочными инструментами (например, `busybox` или `debug-tools`).
    2.  Kubernetes добавляет ephemeral-контейнер в спецификацию пода.
    3.  Контейнер запускается и предоставляет вам оболочку.
*   **Ключевые особенности:**
    *   **Временный:** Ephemeral-контейнеры не перезапускаются и не участвуют в жизненном цикле пода.
    *   **Глубокая интроспекция:** Новый контейнер имеет доступ к файловой системе, сетевому пространству и пространству процессов целевого контейнера.
    *   **Без пересборки:** Вам не нужно изменять образ вашего основного приложения.

#### **Практические примеры**

1.  **Базовая отладка:**
    ```bash
    # Создать ephemeral-контейнер с образом busybox и подключиться к нему
    kubectl debug my-app-pod-7d5b8c9c4-xl2v9 -it --image=busybox
    ```
    После этого вы можете использовать стандартные утилиты (`sh`, `ps`, `netstat`, `curl`) для диагностики.

2.  **Отладка конкретного контейнера:**
    ```bash
    # Если в поде несколько контейнеров, укажите целевой контейнер
    kubectl debug my-app-pod-7d5b8c9c4-xl2v9 -it --image=debug-tools --target=my-container
    ```
    Флаг `--target` присоединяет ephemeral-контейнер к тем же пространствам (PID, network) целевого контейнера.

3.  **Использование привилегий:**
    ```bash
    # Для диагностики, требующей повышенных привилегий (например, захват трафика)
    kubectl debug my-app-pod-7d5b8c9c4-xl2v9 -it --image=nicolaka/netshoot --target=my-container --privileged
    ```
    Образ `netshoot` содержит множество сетевых утилит (`tcpdump`, `dig`, `mtr`).

#### **Заключение**

`kubectl debug` — это must-have инструмент для любого DevOps-инженера, работающего с современными практиками. Он позволяет диагностировать приложения в `distroless` образах, не жертвуя при этом безопасностью. В следующей статье мы рассмотрим `kubectl edit`, который позволяет вносить быстрые правки, но требует осторожности.
