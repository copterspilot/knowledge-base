На основе анализа старой презентации, чата, субтитров и современных практик, вот несколько чек-листов, которые помогут систематизировать процесс диагностики, отладки и проверки работоспособности кластера Kubernetes.

---

### **Чек-лист 1: Базовый цикл диагностики инцидента (Ops)**

Этот чек-лист — основа для любого инженера, сталкивающегося с проблемой в кластере.

**Цель:** Быстро и систематически найти корень проблемы с подом или сервисом.

**Шаги:**

1.  **`kubectl get` — Первичный осмотр:**
    *   [ ] `kubectl get pods` — Найти под в проблемном состоянии (например, `CrashLoopBackOff`, `Pending`, `Error`).
    *   [ ] `kubectl get nodes` — Проверить состояние нод (все ли `Ready`?).
    *   [ ] `kubectl get events --watch` — Наблюдать за событиями в реальном времени.

2.  **`kubectl describe` — Глубокая диагностика:**
    *   [ ] `kubectl describe pod <имя_пода>` — Проанализировать секцию `Events`. Это **ключевая подсказка**. Ищите сообщения типа `FailedScheduling`, `FailedMount`, `Back-off restarting failed container`.

3.  **`kubectl logs` — Анализ вывода приложения:**
    *   [ ] `kubectl logs <имя_пода>` — Посмотреть логи текущего контейнера.
    *   [ ] `kubectl logs <имя_пода> --previous` — **Критически важно!** Посмотреть логи упавшего контейнера, если под рестартует.
    *   [ ] `kubectl logs -l app=my-app --tail=10` — Агрегировать логи всех подов с меткой.

4.  **`kubectl exec` — Взаимодействие с подом (если возможно):**
    *   [ ] `kubectl exec -it <имя_пода> -- sh` — Войти в контейнер и проверить конфигурацию, файловую систему, доступность зависимостей (например, `curl` до базы данных).

### **Чек-лист 2: Диагностика "CrashLoopBackOff"**

**Цель:** Устранить причину постоянного рестарта пода.

**Шаги:**

1.  [ ] **Подтвердить проблему:** `kubectl get pods` — Убедиться, что под действительно в статусе `CrashLoopBackOff`.
2.  [ ] **Проверить события:** `kubectl describe pod <имя_пода>` — Изучить секцию `Events`. Ищите:
    *   `Back-off restarting failed container`
    *   `Liveness probe failed`
    *   `Readiness probe failed`
    *   `Failed to pull image`
3.  [ ] **Анализ логов упавшего контейнера:** `kubectl logs <имя_пода> --previous` — Найти фатальную ошибку (например, `panic`, `Connection refused`, `File not found`).
4.  [ ] **Проверить ресурсы:** `kubectl describe pod <имя_пода>` — Проверить `Limits` и `Requests`. Не превышает ли приложение лимит памяти (`OOMKilled`)?
5.  [ ] **Проверить liveness-пробу:** `kubectl describe pod <имя_пода>` — Проверить, правильно ли настроена `livenessProbe` (путь, порт, таймауты).
6.  [ ] **Проверить конфигурацию и переменные окружения:** `kubectl describe pod <имя_пода>` — Убедиться, что все `ConfigMaps` и `Secrets` смонтированы и переменные окружения заданы верно.
7.  [ ] **Глубокая отладка (если необходимо):** Использовать `kubectl debug` для запуска контейнера с отладчиком (`nicolaka/netshoot`) и анализа системы (`strace`, `tcpdump`).

### **Чек-лист 3: Проверка работоспособности кластера (Health Check)**

**Цель:** Провести регулярный аудит кластера на предмет проблем с его основными компонентами.

**Шаги:**

1.  **Проверка состояния нод:**
    *   [ ] `kubectl get nodes` — Все ноды в статусе `Ready`?
    *   [ ] `kubectl describe node <имя_ноды>` — Проверить `Conditions` (особенно `MemoryPressure`, `DiskPressure`, `PIDPressure`).
2.  **Проверка системных подов:**
    *   [ ] `kubectl get pods -n kube-system` — Все поды в `kube-system` запущены и работают (`Running`, `Ready: 1/1`)?
    *   [ ] `kubectl logs <имя_проблемного_пода> -n kube-system` — Просмотреть логи системных компонентов (kube-apiserver, kubelet, coredns) при необходимости.
3.  **Проверка сетевой связности:**
    *   [ ] Запустить тестовый под: `kubectl run test-pod --image=busybox --rm -it --restart=Never -- sh`
    *   [ ] Изнутри пода выполнить: `ping 8.8.8.8` — Проверка доступа в интернет.
    *   [ ] Изнутри пода выполнить: `nslookup kubernetes.default` — Проверка работы DNS.
4.  **Проверка политик безопасности (если включены):**
    *   [ ] `kubectl get psp` (если `PodSecurityPolicy` еще используется) или проверить конфигурацию `Pod Security Admission` (PSA).
    *   [ ] Попытаться создать под с `securityContext.privileged: true` в namespace с политикой `restricted` — Убедиться, что создание блокируется.
5.  **Запуск аудита безопасности:**
    *   [ ] `kube-bench run` — Проверить соответствие рекомендациям CIS.
    *   [ ] `kubescape scan` — Провести комплексный аудит безопасности.

### **Чек-лист 4: Инструменты для отладки в минимальных образах (Debugging in Distroless)**

**Цель:** Диагностировать проблему в поде, где нет стандартных утилит (`sh`, `bash`, `curl`, `netstat`).

**Шаги:**

1.  [ ] **Использовать `kubectl debug`:**
    *   [ ] `kubectl debug <имя_пода> -it --image=nicolaka/netshoot -- sh` — Запустить временный контейнер с полным набором сетевых и диагностических утилит.
2.  **В контейнере отладки:**
    *   [ ] Проверить сетевые соединения: `netstat -tulpn`, `ss -tulpn`.
    *   [ ] Проанализировать трафик: `tcpdump -i any`.
    *   [ ] Проверить доступность сервисов: `curl`, `dig`, `nslookup`.
    *   [ ] Просмотреть системные вызовы: `strace -p <PID_приложения>`.
3.  [ ] **Использовать `inspektor-gadget` (если установлен):**
    *   [ ] `kubectl gadget trace open -n <namespace>` — Отследить, какие файлы открывает приложение.
    *   [ ] `kubectl gadget trace network -n <namespace>` — Отследить сетевые вызовы.
4.  [ ] **Использовать `ksniff`:**
    *   [ ] `kubectl sniff <имя_пода> --watch` — Захватить сетевой трафик и проанализировать его в Wireshark.

### **Чек-лист 5: Подготовка к удаленной отладке (Remote Debugging Setup)**

**Цель:** Настроить возможность подключать локальный отладчик (IDE) к приложению, запущенному в кластере.

**Шаги:**

1.  [ ] **Настроить приложение:**
    *   [ ] Добавить в манифест `containerPort` для порта отладчика (например, 2345 для `dlv`, 5005 для Java).
    *   [ ] Настроить запуск приложения с флагами отладчика (например, для Go: `dlv --listen=:2345 --headless=true --api-version=2 --accept-multiclient exec ./my-app`).
2.  [ ] **Пробросить порт:**
    *   [ ] `kubectl port-forward pod/<имя_пода> 2345:2345` — Пробросить порт отладчика на локальную машину.
3.  [ ] **Настроить IDE:**
    *   [ ] В VS Code, GoLand или другой IDE создать конфигурацию удаленной отладки.
    *   [ ] Указать хост `localhost` и порт `2345`.
4.  [ ] **Подключиться и отлаживать:**
    *   [ ] Запустить конфигурацию отладки в IDE.
    *   [ ] Установить брейкпоинты и анализировать выполнение кода.

Эти чек-листы можно использовать как шпаргалки для новичков или как основу для создания более сложных runbook'ов в команде.
