Хотя классические **функциональные требования** описывают, *«что система должна делать»* (например: «пользователь может войти в систему», «система отправляет уведомление по email»), **облачные функциональные требования** — это *расширение или адаптация* этих функций с учётом **уникальных возможностей и ограничений облачной среды**.

---

## 🔹 Что такое облачные функциональные требования?

**Облачные функциональные требования** — это функции, которые:
- **Зависят от облачной инфраструктуры** (например, PaaS, serverless, managed services),
- **Используют встроенные облачные сервисы** (базы данных, очереди, AI/ML),
- **Реализуют поведение, невозможное или неэффективное в локальной среде**.

Они остаются "функциональными" (описывают действия системы), но **специфичны для облака**.

---

## 🔹 Примеры специализированных облачных функциональных требований

| Категория                                         | Пример функционального требования                                                                                                         | Объяснение                                                                                 |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **1. Автоматическое масштабирование**             | Система должна автоматически добавлять экземпляры приложения при превышении нагрузки CPU > 75%.                                           | Использует **autoscaling** (AWS Auto Scaling, Azure Scale Sets).                           |
| **2. Управление жизненным циклом ресурсов**       | Администратор может запускать и останавливать тестовые среды по расписанию (например, только в рабочее время).                            | Использует **Scheduled Start/Stop VMs** (Azure), **Lambda + CloudWatch** (AWS).            |
| **3. Серверлесс-обработка событий**               | При загрузке файла в хранилище (например, S3 или Blob Storage) автоматически запускается функция для его обработки (конвертация, анализ). | Использует **AWS Lambda, Azure Functions, Google Cloud Functions**.                        |
| **4. Интеграция с облачными managed-сервисами**   | Система должна использовать облачную управляемую СУБД (например, Azure SQL Database, Amazon RDS) вместо локальной установки.              | Упрощает администрирование, резервное копирование и обновление.                            |
| **5. Глобальное развертывание и маршрутизация**   | Запросы пользователей должны направляться к ближайшему региональному экземпляру приложения через глобальный балансировщик нагрузки.       | Использует **Azure Traffic Manager, AWS Global Accelerator, Google Cloud Load Balancing**. |
| **6. Управление идентификацией в облаке**         | Пользователи должны входить через облачный провайдер удостоверений (например, Azure AD, AWS Cognito).                                     | Поддерживает SSO, MFA, централизованное управление доступом.                               |
| **7. Обработка данных в реальном времени**        | Система должна обрабатывать поток данных (например, с датчиков IoT) в реальном времени с помощью облачного потокового сервиса.            | Использует **Azure Event Hubs, AWS Kinesis, Google Pub/Sub**.                              |
| **8. Использование ИИ/ML как сервиса**            | Приложение должно использовать облачный сервис распознавания изображений (например, Azure Computer Vision, Amazon Rekognition).           | Позволяет добавить ИИ-функции без разработки с нуля.                                       |
| **9. Многооблачное или гибридное взаимодействие** | Система должна синхронизировать данные между Azure и локальной Active Directory через Azure AD Connect.                                   | Реализует гибридную модель.                                                                |
| **10. Самоисцеляющиеся системы**                  | При обнаружении сбоя сервиса система автоматически перезапускает контейнер или переразворачивает приложение.                              | Использует **Kubernetes (AKS, EKS, GKE)**, **health checks**, **self-healing**.            |

## 🔹 Чем отличаются от классических функциональных требований?

| Критерий                     | Классические функциональные требования                | Облачные функциональные требования                                         |
| ---------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------- |
| **Среда исполнения**         | Могут работать в любой среде (локальной, виртуальной) | Зависят от облачной платформы и её сервисов                                |
| **Гибкость**                 | Менее зависимы от инфраструктуры                      | Тесно связаны с возможностями облака                                       |
| **Пример**                   | «Пользователь может загрузить файл»                   | «Файл сохраняется в Blob Storage и триггерит Azure Function для обработки» |
| **Технологическая привязка** | Универсальные                                         | Часто привязаны к конкретному провайдеру (vendor-specific)                 |

---

## 🔹 Почему они важны?

1. **Позволяют использовать преимущества облака**:
   - Автоматизация.
   - Экономия времени на администрирование.
   - Доступ к передовым технологиям (ИИ, IoT, big data).

2. **Повышают эффективность разработки**:
   - Не нужно "изобретать велосипед" — используются готовые managed-сервисы.

3. **Влияют на архитектуру**:
   - Подталкивают к микросервисам, serverless, event-driven архитектурам.

4. **Требуют учёта при миграции**:
   - При переносе legacy-приложения нужно решить: оставить как есть или рефакторить с использованием облачных функций.

---

### 📌 Рекомендации:
- При проектировании облачного решения **включайте облако как часть функциональных требований**, а не только как инфраструктуру.
- Документируйте, **какие облачные сервисы используются** и **почему**.
- Учитывайте **vendor lock-in**: если функция зависит от AWS Lambda — миграция в Azure станет сложнее.
