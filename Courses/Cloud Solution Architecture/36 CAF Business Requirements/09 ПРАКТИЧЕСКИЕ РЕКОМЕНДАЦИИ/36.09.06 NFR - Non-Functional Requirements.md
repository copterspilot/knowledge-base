**Облачные нефункциональные требования (Non-Functional Requirements, NFR)** — это критерии, определяющие **качество, производительность, надёжность и безопасность** системы в облачной среде. В отличие от функциональных требований («что система должна делать»), нефункциональные описывают **«как она должна это делать»** — особенно в условиях масштабируемости, отказоустойчивости и динамической природы облака.

Они играют ключевую роль при проектировании, миграции и эксплуатации облачных решений.

---

## 🔹 Основные категории облачных нефункциональных требований

| Категория                                             | Описание                                                                  | Примеры требований                                                                                                                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Доступность (Availability)**                     | Время, в течение которого система доступна для пользователей.             | - Система должна быть доступна 99.95% времени в год (макс. простой ~4.3 часа/год).<br>- Обеспечить отказоустойчивость на уровне зон доступности (Availability Zones).        |
| **2. Надёжность (Reliability)**                       | Способность системы корректно работать в течение заданного времени.       | - Автоматическое восстановление сервисов при сбое.<br>- Резервное копирование каждые 4 часа.                                                                                 |
| **3. Производительность (Performance)**               | Скорость отклика, пропускная способность, задержки.                       | - Время отклика API не более 500 мс при нагрузке до 10 000 запросов в минуту.<br>- Поддержка пиковой нагрузки в 3 раза выше средней.                                         |
| **4. Масштабируемость (Scalability)**                 | Способность системы увеличивать ресурсы под растущую нагрузку.            | - Автоматическое масштабирование (autoscaling) при загрузке CPU > 70%.<br>- Поддержка роста пользователей на 200% в течение 6 месяцев.                                       |
| **5. Безопасность (Security)**                        | Защита данных, систем и пользователей от угроз.                           | - Все данные должны шифроваться (в движении и в покое).<br>- Многофакторная аутентификация (MFA) для администраторов.<br>- Соответствие стандартам: ISO 27001, GDPR, ФЗ-152. |
| **6. Управляемость (Manageability)**                  | Удобство администрирования, мониторинга и обслуживания.                   | - Все ресурсы должны быть видимы в единой панели мониторинга (например, Azure Monitor).<br>- Поддержка инфраструктуры как кода (IaC) через Terraform или ARM-шаблоны.        |
| **7. Восстанавливаемость (Recoverability)**           | Способность восстановить систему после сбоя.                              | - RTO (время восстановления) ≤ 15 минут.<br>- RPO (точка восстановления) ≤ 5 минут (потеря данных не более 5 мин).                                                           |
| **8. Экономичность (Cost Efficiency)**                | Оптимизация затрат на использование облачных ресурсов.                    | - Ежемесячные затраты не должны превышать бюджет на 10%.<br>- Использование reserved instances для стабильной нагрузки.                                                      |
| **9. Совместимость (Interoperability)**               | Возможность интеграции с другими системами и платформами.                 | - Поддержка REST API и стандартов OAuth 2.0.<br>- Совместимость с гибридной средой (локальные + облачные сервисы).                                                           |
| **10. Гибкость (Flexibility)**                        | Возможность адаптации к изменениям (технологическим, бизнес-требованиям). | - Поддержка развёртывания в нескольких облаках (multi-cloud).<br>- Возможность быстрого переноса приложений между регионами.                                                 |
| **11. Аудит и соответствие (Audit & Compliance)**     | Возможность отслеживать действия и соблюдать нормативы.                   | - Ведение логов всех изменений (audit trail) в течение 1 года.<br>- Хранение данных только в регионах ЕС (для GDPR).                                                         |
| **12. Производительность сети (Network Performance)** | Задержки, пропускная способность, стабильность соединения.                | - Задержка между пользователем и ближайшим регионом — не более 50 мс.<br>- Поддержка ExpressRoute/VPN для защищённого доступа.                                               |

## 🔹 Почему нефункциональные требования важны в облаке?

1. **Облако динамично** — ресурсы создаются, масштабируются и удаляются автоматически. Без NFR возможны "облака хаоса" (cloud sprawl).
2. **Отказоустойчивость критична** — пользователи ожидают 24/7 доступности.
3. **Затраты могут "взорваться"** — если не контролировать масштабирование и хранение.
4. **Безопасность распределена** — ответственность делится между клиентом и провайдером (Shared Responsibility Model).
5. **Глобальное присутствие требует учёта регионов и законодательства**.

---

## 🔹 Как формулировать нефункциональные требования?

Используйте **конкретные, измеримые и проверяемые** формулировки:

❌ Плохо:  
> *Система должна быть быстрой и надёжной.*

✅ Хорошо:  
> *Система должна обрабатывать 5000 одновременных запросов с временем отклика не более 800 мс при 99.9% доступности.*

---

## 🔹 Пример: NFR для веб-приложения в Azure

```markdown
- Доступность: 99.95% (SLA), реализовано через Availability Zones.
- Производительность: время отклика API ≤ 600 мс при нагрузке до 8000 RPS.
- Безопасность: шифрование данных (AES-256), MFA для администраторов, защита от DDoS (Azure DDoS Protection).
- Масштабируемость: autoscaling от 2 до 20 экземпляров в зависимости от CPU.
- Восстанавливаемость: RTO ≤ 10 мин, RPO ≤ 1 мин (через Azure Site Recovery).
- Соответствие: хранение персональных данных только в регионе "Западная Европа", соответствие GDPR.
- Затраты: бюджет на инфраструктуру — не более 15 000 руб./мес., с оповещениями при превышении 80%.
```

## 🔚 Вывод

**Нефункциональные требования — это фундамент успешного облачного решения.**  
Они определяют, насколько система будет:

- 💪 Устойчивой к сбоям,  
- ⚡ Быстрой и масштабируемой,  
- 🔒 Безопасной,  
- 💰 Экономически эффективной.

Их игнорирование ведёт к техническим долгам, срыву сроков, перерасходу бюджета и утечкам данных.
